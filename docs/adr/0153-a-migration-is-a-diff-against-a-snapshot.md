# 0153 — a migration is a diff against a snapshot, not a database

**Status:** accepted
**Amends:** the refusal recorded in the Rows section of
[`docs/reference.md`](../reference.md), that a Row may not declare an index or a
constraint; and with it two sentences written back when there was no migration
runner — [ADR 0039](./0039-the-shape-of-a-query-is-settled-while-compiling.md)'s
closing "migrations are not here and are not implied", and the aside in
[ADR 0078](./0078-a-uuid-is-whatever-the-database-stores.md) that there is none.
Both stand as the record of what was true then. The pages that describe the code
change when the code does, not before.

## Context

`nilo_sql` has had half a migration tool for a year. `schema.compare` reads the
catalog through a Dialect's `introspect`, knows which column types each Zig type
may be read out of, and reports a column that is missing, wrongly typed or
wrongly nullable. It cannot look the other way, at a column the table has and
the Row dropped, and `dialect.accepts` answers with the **list** a column may be
read out of, where `CREATE TABLE` needs the one to write. The machinery exists
and points one way.

What a caller does meanwhile is on file. `stress/arsip` creates its one table in
ten lines: stand up `std.Io.Threaded`, open a second `Db` on the same file,
`nilo_start` it by hand, run the DDL, close it again. The statement went through
`db.raw(Account, run, schema, .{})`, passing the Row of the table being created
to something that answers no rows, because `raw`'s first argument is a Row and
there was nothing else to pass. `db.exec` closed that half and the rest did not
move.

The second half of the same finding is the expensive one. arsip's `accounts`
table declared `id INTEGER PRIMARY KEY AUTOINCREMENT`, which SQLite reports as
nullable, and `id: i64` is not. Forty tests passed in both optimize modes
against that schema; the first `zig build run` stopped with the right sentence.
`db.checking` is the check and `listen()` is what runs it, so a suite that never
listens never checks.

[ADR 0079](./0079-there-is-a-phase-before-the-server.md) settled **where** a
migration runs: `app.start(io)` opens the pools and comes back, so a program can
migrate between starting its services and taking a socket. What it did not
settle is what a migration **is**. The roadmap listed three questions with no
answers and said the other two waited on the first. This decides all three.

## Decision

**A migration is generated by diffing the caller's types against a snapshot the
repository holds. The database is not consulted, and `generate` runs with no
connection anywhere.**

### There are two records, because there are two questions

Most tools keep one and get confused where the two disagree.

| Record | Where it lives | The question it answers |
|---|---|---|
| `nilo_migrations` | in the database | which versions are applied **here** |
| `migrations/snapshot.zon` | in git | what the last `generate` believed the schema was |

The snapshot is what makes `generate` need no database, no shadow copy of one,
and no `DATABASE_URL`. It also gives the two-branch case a real answer: two
branches that each generate version 8 against the same parent conflict in git,
in `snapshot.zon` and in the generated manifest, which is a conflict worth
having. `check` fails naming both, and `rebase` writes the second one again on
top of the merged snapshot as version 9.

Integrity is a hash per version over its own steps plus its parent's hash.
Editing a version that has already been applied is a red build rather than a
surprise in production.

### A rename is written in the type

A diff cannot tell a rename from a drop and an add, and nothing will change
that. drizzle-kit asks the developer at the prompt. That is refused here for one
reason: two developers can answer differently for the same code, and neither
answer reaches the pull request.

```zig
pub const nilo_table = .{
    .name = "users",
    .key = .id,
    .was = .{ .email = "e_mail" },
};
```

`generate` writes `ALTER TABLE "users" RENAME COLUMN "e_mail" TO "email"`, and
only while the snapshot still has `e_mail`. Once it does not, the tool says the
entry is spent and can be deleted. A `.was` naming a column the Row does not
have is a Refusal, so the common mistake stops at compile time.

### A version is a list of steps, and one file holds the list

A data migration cannot be derived from a struct diff and should not be
attempted. So a version is not one blob. It is a list, and the hand-written step
sits in the list beside the generated ones:

```zig
// migrations/0007_split_name.zig — written by `db generate`, then edited.
pub const version: migrate.Version = .{
    .number = 7,
    .name = "split_name",
    .steps = &.{
        .{ .kind = .add_column, .why = "User.first_name", .sql =
            \\ALTER TABLE "users" ADD COLUMN "first_name" text
        },
        // Written by hand. `generate` never produces a `.data` step.
        .{ .kind = .data, .why = "split name into its two halves", .sql =
            \\UPDATE "users" SET "first_name" = split_part("name", ' ', 1)
        },
        .{ .kind = .drop_column, .why = "User.name is gone", .destructive = true, .sql =
            \\ALTER TABLE "users" DROP COLUMN "name"
        },
    },
};
```

All of it applies in order inside one transaction. This is the shape that makes
expand and contract expressible, which `up`/`down` cannot: the data step sits
**between** two DDL steps, and a pair has nowhere to put it.

**The version carries no hash**, and the file above does not name one. A hash a
caller can fill in is a hash a caller can fill in wrong, and a wrong one leaves
the drift check running and answering nothing. `migrate.chainOf` walks the list
once and is the only thing that computes one; what it hands back is a `Chain`,
which is what `applyPending` and `drift` take. A generated file that a reviewer
reformats then hashes the same, because the hash is over the SQL and not over
the file's bytes.

**One Zig file per version rather than one `.sql` file per step**, and the
reason is the statement boundary. Every statement this module sends is prepared
([ADR 0057](./0057-a-statement-that-is-a-constant-can-be-prepared-once.md)), and
a prepared statement is one statement, so a `.sql` file holding three of them
has to be split before it can run. Splitting on `;` is wrong for real SQL — a
semicolon inside a string literal or inside a Postgres `$$…$$` body is not a
boundary — so it needs a lexer. **And the failure that lexer produces is the
worst shape available**: `sqlite3_exec` runs several statements happily and the
Postgres extended protocol does not, so a leaky splitter passes on a laptop and
fails in production. The alternative without a lexer is one statement per file,
which puts a first migration of ten tables at about thirty files.

Here the boundary is an array element and nothing is parsed. The `why`, the
kind, the `destructive` flag and the SQL are also next to each other, so a
reviewer reads one file rather than a manifest and a directory.

What that costs is a plain `.sql` file: this one cannot be fed to `psql -f`, and
an editor will not colour SQL inside a Zig string. `db status --sql` prints the
plain statements for the review that wants them. A generated `.sql` written
*alongside* the Zig file was rejected — two copies of the same statement is a
pair that can drift.

It costs one more thing, and it is the only friction in the whole loop.
`migrations/manifest.zig` is what the tool imports and what `generate` writes,
so it has to exist before the first build, which is before the first `generate`.
That is seven lines written once — `head` at 0, an empty list, and the `chain`
function — and from then on the file is the tool's. The alternative is a build
step that walks the directory and writes the manifest, which removes the seven
lines and the merge conflict two branches get in that file, and adds a public
build-time API every dependent has to call. Roadmap work; the seven lines are
not enough pain to buy it yet.

**A step that has to run Zig rather than SQL is not expressible yet**, and was
not under the file layout this replaces either: the earlier `0007_split_name.b.zig`
named a file and not a mechanism, and `Step.sql` is text with nowhere to put a
function. Re-hashing every password with `nilo_pw` is the case that wants it. It
is roadmap work, and the shape it needs is a `Version` whose pieces are a
comptime tuple of steps and functions.

### Forward only, and the debt that creates is paid in two commands

There is no `down`. A generated one is a lie for anything destructive, the data
is already gone, and a script nobody has ever run is the worst thing to reach
for during an incident. `generate` refuses a destructive step until the caller
asks for it by name, and records the ask in the generated file's header so a
reviewer sees it.

The honest argument for `down` is the local loop rather than production, and it
is answered rather than dismissed: `reset` drops the objects nilo owns and
replays from zero, and `squash` folds applied history into one baseline so a
reset stays quick at the two hundredth version. The snapshot knows which objects
are nilo's, so a reset leaves hand-written SQL alone.

### The line: nilo generates what a type can say

**A word gets into the marker if the compiler can check it**, which is this
repository's own thesis applied to schemas, and it settles the vocabulary at
three:

```zig
pub const nilo_table = .{
    .name = "users",
    .key = .id,
    .unique = .{ .{ .email, .ignoring_case } },
    .index = .{ .{ .tenant_id, .created_at } },
    .references = .{ .org_id = .{ Org, .id } },
};
```

`.unique` and `.index` are checked against the Row's own columns. `.references`
is checked harder: `Org` has to be a Row, `.id` has to be one of its columns,
**and `org_id`'s Zig type has to be the same as `Org.id`'s**. A foreign key
whose types do not line up is a bug that surfaces at the first insert in
production, and here it does not compile. The tuple shape is the one
`conflictColumns` already reads for an upsert target, so it is not new spelling.

`.ignoring_case` is a modifier rather than a fourth word, and it is where the
Dialect earns its seam: SQLite writes `(email COLLATE NOCASE)` and Postgres
writes `(lower(email))`, because the two databases genuinely do it differently.
arsip's own table needed exactly this and is the caller that brought it.

Everything else is not a gap. A check constraint, a partial index, a collation
on a column, a generated column, a trigger, a view, an extension: those are SQL
written into a step, and **the snapshot marks them as objects nilo does not
own, so a diff never tries to drop one.** That last clause is what keeps the
vocabulary closed. A fourth word needs a caller with a case and a check that can
run while compiling, which is the same bar every other feature here has had.

**A default belongs to the step, not to the type.** It looks like a property of
the column, and the moment it is actually load-bearing is narrower than that: a
`NOT NULL` column added to a table with rows in it fails without one. That is a
fact about one migration, often dropped afterwards, so putting it in the marker
would keep something true once for the life of the program.

Only a Row that owns a `.name` may carry the three words. A Row that borrows
another (`nilo_table = User`) may not, and that is a Refusal. That is what
amends the reference: what was refused is a **query type** declaring schema, and
that stays refused. The table's own type declaring the table does not.

### The binary knows which version it was built against

`generate` also writes `migrations/manifest.zig`, ordinary Zig the caller
commits, holding the version list as comptime constants. A server that imports
it has its expected version as a number inside the binary before the program
runs, and one query at boot says whether the database agrees:

```
error: nilo_sql: this binary was built for schema version 9, the database is at 7.
  Not yet applied: 0008_add_tenant, 0009_split_name.
```

Deploying code ahead of its migration is an incident with one shape, and almost
nothing catches it. The other direction, a database ahead of the code, is
allowed and logged, because that is what expand and contract is for.

### It lives in `sql/`, and a standalone module was refused

A `nilo_migrate` module would import `nilo_sql`, which is a sibling at the
Service layer, and `zig build layering` refuses that correctly
([ADR 0042](./0042-the-bottom-layer-holds-more-than-one-module.md)). So the code
is `sql/migrate.zig`, and the linker drops it for a program that does not name
it. That is the argument `sqlite.zig` already makes and `zig build size-sql`
already proves at 524,840 bytes.

It needs one new declaration on the Dialect contract, `columnType(T)`, and it is
a declaration of its own rather than a rule over `accepts`. The two answer
different questions: a Row reading `i32` accepts `int4` and `int8`, and creating
one writes `int4`. `dialect.zig`'s header says the last three declarations to
arrive were all found by compiling a write rather than by reading the file, and
this one should be expected to go the same way.

## What was rejected

**An interactive prompt for renames**, which is drizzle-kit's answer and Django's.
It moves a decision out of the diff and into somebody's terminal, so the same
code produces different migrations for different people.

**Down migrations**, for the reasons above. The narrow case where a reversal is
genuinely correct is real: `CREATE INDEX` reverses exactly, always, and
`ADD COLUMN` does while nothing has written to it. What nobody ships is a tool
that tells the two apart, and the shape that would is `undo` refusing a version
holding a single step it cannot reverse. That is a mechanism for a case nobody
has brought, so it is written down and not built.

**A full DDL vocabulary in the marker.** It is the shape with the least
hand-written SQL and it fails the compiler test at its second entry: a check
constraint and a literal default are strings the database reads, so nothing
about them can be checked while compiling. A vocabulary that stops being checked
starts growing, and then every disagreement between two databases becomes a
decision here. `.index = .{ .{ .cols = .{.email}, .where = "deleted_at IS NULL" } }`
is also harder to read than the SQL it replaces.

**A shadow database**, which is how Prisma computes a diff. It needs a second
database to exist wherever the diff is computed, including in CI and on a
laptop with no server running, and the snapshot answers the same question
without one.

## What it costs

Nothing on any of the four axes ([ADR 0018](./0018-the-trade-budget-has-three-axes.md)),
and for once that is a fact about the shape rather than a budget that was met.
The tool is a second executable in the caller's own repository, so it is not in
the process those axes measure.

| Axis | Cost |
|---|---|
| Allocations per request | 0 |
| Memory per idle connection | 0 |
| Throughput and p99 | 0 |
| Binary size, the server | 0 bytes, measured |

The binary-size row is measured rather than reasoned. `zig build size-sql`
builds two stripped `ReleaseFast` programs that import `nilo_sql` and never name
`migrate`, and the same two built from the commit before this module landed come
out byte for byte identical: **1,785,640 for `pg_only` and 2,291,696 for
`sqlite_only`, both sides**. Nothing here is reachable from a program that does
not call it, so nothing here is in it
([`bench/result/sql.md` §10](../../bench/result/sql.md)).

One thing is still unmeasured, and only for a program that names it.
`applyPending` runs in process, between `app.start(io)` and `listen()`, which is
what a SQLite application needs because there is no server to have run the DDL
elsewhere. It carries the step text through `manifest.zig`, so that application
ships one file. What the 0 above measures is a server that never calls it; what
a server that *does* pays has no number yet, and it goes in
`bench/result/sql.md` beside the write half's 53 KB when somebody takes it.

What can be got wrong on speed is the applying, and it is bounded by naming it:
one round trip to read the applied set rather than one per version, one
transaction per version, and one advisory lock taken once. The lock is not
decoration. The in-process path is exactly the case where ten replicas boot at
the same moment, and it is the part a hand-written runner usually leaves out.

`generate` and `check` touch no database and no network, so their cost is
reading the snapshot and the step files. That is the pair CI runs on every pull
request, and it is the number worth having first.
