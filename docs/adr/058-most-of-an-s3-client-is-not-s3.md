# Most of an S3 client is not S3

**Status:** accepted
**Topic:** [s3](../design/s3.md)

## Context

S3 is an HTTP API, so a module that speaks it needs an HTTP client. nilo has an HTTP *server* and cannot lend it: `http/http1.zig` parses request lines and writes responses, the other direction, and a Service may not import `nilo_http` sideways. The tempting reading is that the missing piece is small, since nilo already knows how to find the end of a head and decode a chunked body, and that code is measured and fast. It was checked and found not to hold.

`http/http1.zig` is 1,068 lines, 686 of code across 28 tests. Split by whether a client could use it, the framing, header iteration and chunked codec a client would want is about 165 of them, twenty-four per cent; the rest is a request line, response writing and server policy. The fast part is not even in that 165: it is in `scan.zig`, whose numbers are about a server's problem, a hostile client dribbling a head in one byte at a time. An S3 client reads one response head of a few hundred bytes per call over a round trip of 5–50 ms, where the measured saving is 130 ns, 0.0007% of that, well under the 10% bar ([ADR 017](./017-the-trade-budget-has-four-axes.md)). And what reuse would not touch at all is where the cost actually is: TLS plumbing (~380 lines) and a connection pool (~250), against 0 for either from `std.http.Client`. Framing is a fifth of the job; the two expensive parts, where the bugs and the memory are, get nothing from sharing anything.

The bucket, the key type and signing were designed before this module existed ([ADR 059](./059-a-bucket-is-a-type-and-a-key-is-not.md), [ADR 060](./060-a-signing-key-changes-once-a-day.md)); this decision is what it sits on and speaks through, and what does and does not belong in it.

## Decision

### `nilo_s3` is SigV4, S3's semantics, and nothing else

**The client is `nilo_fetch`, itself `std.http.Client` with policy in front of it, and the TLS underneath is `std.crypto.tls.Client`.** That keeps this module's own dependency count at zero: not one, zero, since `nilo_fetch` is code in this repository rather than an entry in `build.zig.zon`, and a program importing `nilo_s3` downloads no package a program importing `nilo_http` does not.

Three properties were checked before this design was chosen, because any one of them failing would have ended it. **SigV4 needs the request written byte for byte**: a client that reorders or adds headers invalidates the signature, and every default header in `std/http/Client.zig` is overridable, with `extra_headers` written out verbatim, in order. **A handler must not block its thread** ([ADR 013](./013-handlers-must-not-block-the-thread.md)): the connection pool takes an `Io.Mutex`, which parks the fiber under zio rather than blocking it. **One allocation per connection**: all four buffers are sliced out of a single `alignedAlloc`.

### What is left here is signing and the bucket

The gate on calls in flight, the deadline, the bounded drain of a refused body, and the retry onto a connection the peer had already reaped are not this module's: they are `nilo_fetch`'s, because `nilo_s3` is a caller of the Fitting rather than the owner of an HTTP client ([ADR 061](./061-a-fitting-borrows-the-loop.md), [ADR 063](./063-an-object-store-is-a-service-that-dials.md)). Two of those were designed here first and carried the reasoning that still holds where they now live: the per-connection memory a pooled HTTPS connection costs, which is why a gate has to exist at all and why its ceiling is stated as a number in the docs rather than left implicit; and the bound on the retry, one attempt per connection the pool could be holding rather than one attempt flat, because a whole pool reaped together lets a single retry draw a second corpse as often as a live one. The retry's condition was also widened here first: a reaped connection arrives as a FIN, which `std.http` names `error.HttpConnectionClosing`, or, when this end wrote before the peer's `close` landed, as an RST that surfaces as `error.ReadFailed` with nothing buffered: the same reaped connection, the same nothing answered, and the narrower reading missed the second spelling until a benchmark against `bench/s3_server.zig` after 80 seconds idle found it. A third spelling is a request with a body, which flushes its head before the body: the peer's RST comes back between the two and the body write fails as `WriteFailed`, so a `putForm` or `postJson` as the first call after a quiet spell failed every time (found by a test that sleeps until the peer's close has landed); it counts only on a connection taken from the pool, never on one the call dialled, and only when no head came back. All of it, `Exchange.nothingCameBack`, the pool-sized retry bound and the per-connection byte accounting, is `fetch/fetch.zig` now; its own doc comments carry the numbers and the history, and this ADR does not restate them.

A `503 SlowDown` or a 5xx comes back to the handler as `error.Throttled` or `error.Unavailable`, and by default it is not retried: a fiber that slept while holding a permit would turn throttling into a queue, and a streamed `put` cannot be retried anyway, its reader already consumed. A Store that says `Options.retry` retries the calls whose bytes are in hand, under `nilo_fetch`'s mechanism and with the permit given back across each wait ([ADR 271](./271-a-retry-is-the-callers-numbers-and-nilos-mechanism.md)); the streaming calls and the multipart protocol are never retried. For the same reason it is never sent on a pooled connection at all: a socket the server closed while it idled would eat the reader and fail, and no replay can follow, so a `.stream` body takes a connection of its own (`nilo_fetch`'s `Client.fresh`, whose pool keeps nothing), which cannot be stale. It costs one handshake per streamed body, which is noise against a body big enough to be streamed. Returning immediately is what lets a handler shed load, answer from a cache, or serve a default.

### `list` is a page with a cursor, and nothing here follows it

`nilo_s3` shipped without `LIST`, on the record: a list result is XML, a type AWS wrote rather than one the caller did, and the one call with unbounded output, a helper that walks a bucket being a helper that invites treating a bucket as a database. The caller that closed the gap arrived as a shape: a durable tier with a retention policy, where an object unlinked from the hot copy has to be deleted from the durable one, and after a crash or a partial upload the only way to learn what actually landed is to ask the bucket. Without `list`, a durable replica grows forever and cannot be reconciled; a 64,000-line observability platform weighing a move onto nilo counted 24 call sites for it.

**`bucket.list(c, .{ .prefix, .max_keys, .cursor })` answers one page, `objects` and `next`, and nothing here follows `next` for the caller.**

- **One page, bounded three ways.** At most `max_keys` objects and at most `keys_max` (1,000, S3's own ceiling); a number over it is `error.Rejected` rather than silently clamped, because a server quietly answering fewer would leave a loop that never learns it was capped. The body is read into the Scope up to a ceiling derived from `max_keys` and the bucket's `key_max`, so a server answering more than the question is `error.TooLarge` rather than an arena it fills. The cursor comes back as text; there is no `listAll`, no iterator that dials again. The loop is the caller's.
- **Five names, scanned for, not parsed.** `<Key>`, `<Size>`, `<ETag>`, `<LastModified>` inside each `<Contents>`, and `<IsTruncated>` beside `<NextContinuationToken>` outside them, the same style `code.zig` already used for an S3 error body. No tree is built and anything else the server says is stepped over. `s3/listing.zig` holds the XML so `bucket.zig` holds none.
- **Two encodings, each handled where it arises.** The request asks for `encoding-type=url`, so a key comes back percent-encoded and is decoded by Core's `percent`, the same coding it left on, **but only when the answer echoes `<EncodingType>url</EncodingType>`**: a server that ignored the parameter sends keys as they are, and decoding those turns a literal `%41` into `A`. **A page that says `IsTruncated` and gives no usable `NextContinuationToken` (missing, empty, or past `cursor_max`) is `Failed`, not the last page**: a loop over a bucket cannot tell a listing that stopped early from one that finished. An ETag is not covered by that and arrives as `&quot;…&quot;`, so the five entities XML predefines are unescaped for it and for the cursor and nothing else; a reference that is not one of the five is left as the bytes it was, because a value that fails to decode is still a value and refusing it would refuse the page.
- **The query is canonical by construction.** SigV4 signs the query string sorted by name and encoded, and `listing.query` writes the five parameters in alphabetical order from a fixed list rather than sorting at run time, the same reason `SignedHeaders` is a walk rather than a sort.

`Listed.etag` comes back quoted, the way `head` and `get` hand it back, so a value from a page goes into `getIf` as it is; `last_modified` stays the server's text, read by `sql.Timestamp` for the one caller who wants arithmetic on it.

### Multipart is a protocol, and one call owns it whole

Multipart shipped the way `list` did: refused as a document format until a caller arrived with the shape that needs it. The caller is a dataset version-control system whose items are files of any size, stored once by hash; its server moves manifests and exports that can pass 5 GB, which is S3's ceiling on a single PUT, and `putStream` requires a length a pipeline does not always have. The same observation that let `list` in covers it: the initiate answer is one interesting name (`<UploadId>`), the completion request is a fixed document written out, and the completion answer is one name checked for. `s3/multipart.zig` holds all three so `bucket.zig` holds none, the split `listing.zig` made.

**`bucket.putMultipart(c, key, .{ .reader, .content_type })` is the whole protocol — initiate, parts, completion, and an abort on the way out of a failure — and none of the three steps is public.** Exposing them would hand every caller the three mistakes the call exists to make impossible:

- **A 200 on the completion is not a completion.** S3 can answer `CompleteMultipartUpload` with 200 and an error in the body — the trap this ADR pinned to `COPY` — so the body is read, bounded, and has to say `CompleteMultipartUploadResult` and not `<Error>`; anything else is `Failed` with the reason in the log.
- **A failed upload is aborted, not abandoned.** Parts already up are paid-for bytes that no `list` of keys shows and no `delete` of the key removes; a bucket with no lifecycle rule keeps them forever. The abort is best effort and the original error stands, with a log line naming what remains when even the abort fails.
- **The bounds are held where they can be.** A part under S3's 5 MiB floor is refused by the server at completion time, after everything went up, so `putMultipart` refuses it before any byte moves. The 10,000-part ceiling is the one bound only a server could hold early: for a reader of unknown length it can only be met on the way, after those parts went up, and what the call adds is the honest refusal (`Rejected`, naming `.part_bytes` as the fix) instead of part 10,001 refused by the server.

The parts go over the pooled connections, not a fresh one: a part is bytes in hand, so the reaped-connection retry that covers every slice body covers it, which is the retry a streamed body can never have. Each part and the completion run under the source's optional `.timeout_ms` and the Store's `stall_ms`, the terms ADR 060 set for `putStream`'s one body, because the Store's `timeout_ms` is for the short calls and an 8 MiB part on a slow uplink is not one; on AWS the completion itself can take minutes while the object is assembled. What is held for the whole call is one stream share, the bound `putStream` honours, because an upload that takes minutes is the shape `max_streams` exists for. The three queries are written canonical from fixed lists (`uploads=`, `partNumber=…&uploadId=…`, `uploadId=…` — each already in byte order), the same reason `listing.query` never sorts, and each is written into the URL buffer once and sliced back out for signing, the one-buffer shape `urlForList` set.

**A source that ends inside the first part becomes a plain `put`.** The first part is read before anything is sent, so a source that fits under `part_bytes` has a known length after all: it goes up as one PUT, one round trip instead of three, and its ETag stays the content's own MD5 rather than a multipart digest, which matters to a caller that stores by hash. The empty source is the same case, one empty PUT, so multipart proper always has a full first part. That PUT keeps the transfer's terms, not the short call's: it runs under the source's `.timeout_ms` and the Store's `stall_ms` through the bounded body `put` itself now delegates to, and it takes the stream share — up to a whole part on a slow link is the shape `max_streams` exists to bound, and the caller chose the transfer call.

### Copy and compose: inside the store, and the 200 that is not one

`COPY` came in the same way, with the same caller: its server verifies each upload by reading it once, through a hash, from a staging key, and then needs those bytes at their final key. Without a copy that is a second download and a second upload of every byte, through the server's disk; with one, the store moves them. Uploads arrive in 64 MiB pieces, so joining pieces is the same need, and S3 has it as a multipart upload whose parts are copies.

**`bucket.copy(c, from, to)` is CopyObject, and `bucket.compose(c, to, parts, object)` is the whole join — initiate, `UploadPartCopy` per part, completion, and an abort on the way out of a failure.** Both are one PUT naming its source in `x-amz-copy-source`, signed in its sorted place among the headers, and both carry the trap this ADR pinned to `COPY` from the start: the answer is a document, and a 200 can hold an error. So `copy` reads its bounded body and must find `CopyObjectResult`, and each part copy must find a non-empty `<ETag>`, entity-decoded the way `list` decodes a key, before the completion lists it. What `compose` adds to `putMultipart`'s protocol is only where the bytes come from; the initiate, the completion check and the abort are the same code.

- **A copy keeps its source's type; a join has none to keep.** CopyObject's metadata directive defaults to `COPY`, so the new key is what the old one was. A multipart upload starts with no object at all, so `compose` takes what the joined object is, `.content_type` required and `.cache_control` and `.content_disposition` optional, exactly what `putMultipart`'s source carries, and refuses at compile time without the type (`s3/refusals/a_compose_without_a_content_type.zig`). Otherwise the object would get the store's default type silently.
- **The bounds are S3's, held before a socket where they can be.** One copy is up to 5 GiB; a join takes 1 to 10,000 parts, every one but the last at least 5 MiB, each at most 5 GiB. A part count outside 1 to 10,000 is `error.Rejected` before anything is sent. The sizes are the sources' and only the store knows them, so the store refuses those.
- **A copy has no whole-call limit; `stall_ms` alone bounds it.** The store copies while the request waits: seconds for a large object on SeaweedFS, which moves the bytes. A whole-call limit would cut a copy that is working, and worse, the store can finish a copy the caller was told failed, or a `compose` aborts after copying parts. So each copy request passes `.timeout_ms = 0` explicitly, as `stream`, `putStream`, `putPart` and `completeMultipart` do, because left unset it falls back to the Store's `timeout_ms` (30 s by default); a canned test holds a copy past a 150 ms Store timeout and sees it complete. What a store sends while it copies is the store's: AWS documents that a copy's 200 can come before the copy is complete and carry an error, and that a `CompleteMultipartUpload` is kept alive with whitespace while it is processed, but documents no keep-alive for a copy. A store that keeps a long copy's connection quiet needs a `stall_ms` that long; the reference says so. The checks find their document anywhere in the answer, so leading whitespace is read past.

## What was rejected

- **Write an HTTP/1.1 client inside `s3/`.** About 815 lines of code whose subject is not S3, to save roughly 17 KB per pooled connection (a hand-rolled client shares buffers std keeps separate), bought with a TLS state machine and a connection pool to keep correct forever.
- **A shared `nilo_http1` in the bottom layer.** Better than writing it twice, and still dominated: it shares the fifth of the job that was never the problem, and it forces `readHead`'s signature open to take `bulkhead.Deadlines`, which a bottom-layer module cannot name.
- **ianic's `tls.zig` instead of std's.** More mature and tested against badssl, with levers std lacks (cipher suite selection, client certificates, key logging), and already used by `pg.zig`. Refused on a mechanical fact: `pg.zig` pins it at a fixed commit, Zig deduplicates packages by hash, and a program using both `nilo_sql` and `nilo_s3` under two different pins would compile two TLS implementations into one binary. std's `Options` also ask for exactly the two things this repository already provides, entropy ([ADR 042](./042-entropy-belongs-to-the-loop.md)) and the wall clock ([ADR 041](./041-core-knows-what-time-it-is.md)).
- **Terminating outbound TLS in front**, mirroring [ADR 027](./027-tls-is-terminated-in-front.md). A sidecar that originates TLS is a real deployment shape, and a module that only reaches S3 through one would not do the ordinary job it exists for.
- **Stabilising the flaky test and leaving the retry condition alone.** The reaped-connection test failed about one run in three under `zig build test-all` and passed every time under `zig build test-fetch`; the obvious fix is to stabilise the test, and it would have made CI green while leaving a real call, against a real service that reaps idle connections, failing on a coin toss. The flake was the symptom, not the fault: `test-all` opens more sockets at once than `test-fetch`, and the extra scheduling delay was enough to change which of the two spellings the reap arrived as.
- **Retrying on `ReadFailed` generally**, without checking that nothing was buffered. A reset partway through a head is the same error with bytes already read, meaning the server did answer, so re-sending it would be a retry policy rather than transport hygiene.
- **Retrying on `error.WriteFailed`.** A write to a socket the peer has already dropped is a third spelling of the same race, and part of the request may already have reached the far side; so it is not retried. What a failed write does get is one read of the head: a server may refuse a large PUT on its head and close with the body unread (Garage answers a wrong region this way, `400 AuthorizationHeaderMalformed`), and the refusal is already in the receive buffer when the write fails. `Exchange` reads it once under the call's own deadline and returns it when it is a refusal (not a 2xx, which would be a success for an upload never received whole), marks the connection closing, and otherwise reports `WriteFailed` as before, so `nilo_s3` can turn the answer into `Rejected` instead of an unreachable server. The write succeeding costs nothing extra: the read is on the error path only.
- **Replaying a reader body onto a second connection, or keeping a streamed body on the pool.** A reader is consumed by the first attempt, so a pooled connection the server closed while it idled would fail the one body that can never be sent twice, and a replay would send a different body. A `.stream` body (and so `putStream`) goes on `Client.fresh`, a second std client whose pool keeps nothing: every such call opens a connection of its own, which cannot be stale, and closes it after. It costs one TCP handshake, plus TLS over `https://`, and the client is idle until the first streamed body; calls with a slice or no body keep the pool and its retry.
- **A `sleep` in the test to lose the FIN/RST race on purpose.** A sleep long enough to lose the race on one machine silently stops losing it on a slower one, so the test would keep passing through the FIN branch while claiming to cover the RST one. Reading exactly one byte of the second request through a one-byte buffer proves the request arrived without draining the rest of it into user space, which is what actually exercises the branch; the ordinary 4 KB buffer passed even with that branch switched off, because a receive queue read into user space closes with a FIN like any other.
- **Following the list cursor inside the call**, as an iterator or a callback. Refused as the whole of what "bounded" means here: the one call with unbounded output would be back, the shape that turns a bucket into a table.
- **Reading the list XML with a parser.** There is none in std, and a dependency for five names would be the first `nilo_s3` has that `nilo_fetch` does not; a fixed, flat document is a scan.
- **Leaving a listed key as XML text and unescaping it.** Works, but puts every key with an `&`, `<` or `>` through an unescape that has to be right about five entities and silent about the rest; `encoding-type=url` puts it through a decoder the module already owns and tests.
- **`start-after` instead of `continuation-token`.** Reads nicer in a log and was what S3's V1 offered, but V2 hands back a token on a truncated page, every implementation optimises for it, and making the caller reach for the last key of a page to build the next request is the loop written wrong once per program.
- **Clamping `max_keys` to 1,000** rather than refusing a larger one. What S3 itself does, and what the guide would then have to warn about: a loop sized for 5,000 gets a thousand and no signal that it was capped.
- **Exposing initiate, part and complete as three calls.** The protocol's invariants live between the steps — abort on the way out, the completion body checked, parts counted against the ceiling — and three public calls put every one of them in the caller's hands. The caller who needs resumable or parallel parts is a different shape (presigned part URLs handed to another process) and brings its own design when it arrives.
- **Growing `putStream` a multipart mode when `.len` is absent.** The length is a comptime requirement there, so absence is a compile error, not a branch; and the two calls have different costs (a part buffer and a stream share for minutes against neither), which a caller should choose between by name.
- **Copy as download-and-upload when the store cannot copy.** Every S3 store a caller has brought copies; a fallback that silently moves every byte twice is the cost the call exists to remove, and a store that cannot copy should fail loudly rather than slowly.
- **`compose` taking no metadata, documented as the store's default type.** The caller that asked for it stores files a browser downloads, where the type is what the browser sees; and `putMultipart` already asks for the same three fields for the same reason.
- **Buffering the last part to enforce the 5 MiB floor early.** The floor binds every part but the last, so only a server can know whether a short read is the tail or a violation; the refusal here is on `.part_bytes`, which is known before any byte moves.

## What it costs

Against [ADR 017](./017-the-trade-budget-has-four-axes.md)'s four axes, for a program that imports `nilo_s3`; a program that does not pays nothing on any of them, since `nilo_http` does not name it and the linker never sees it.

| Axis | Cost |
|---|---|
| Allocations per request | 1 for a bounded `get`, sized from `content-length`; 0 for a streamed `get` or a `put` from a slice. A `list` page adds 2 in the Scope (the body, sized by `Exchange.take`, and the page, sized by a count made before it is allocated) plus 1 per key and 1 per ETag for percent- and entity-decoding. A `putMultipart` adds the part buffer (`.part_bytes`, the large one and the point of the call), one ETag copy per part, the completion document sized exactly by `completionLen`, and the two bounded answer bodies; an abort, which only runs on a failure path, builds its URL in the Scope rather than on the stack, so it can carry even an `UploadId` the part calls refused as too long. A `copy` adds 2 in the Scope: the encoded `x-amz-copy-source` (at most 2 + bucket name + 3× the key) and the bounded answer body (at most 8 KiB). A `compose` adds that pair per part, plus one ETag copy per part, the initiate's answer and the completion document, the same as `putMultipart` without the part buffer. |
| Memory per idle connection | 0 added by this module on an inbound connection. The per-process ceiling a pooled outbound connection costs is `nilo_fetch`'s to state ([ADR 061](./061-a-fitting-borrows-the-loop.md)); measured with a Store held, `nilo_s3` linked costs an idle connection nothing over the framework's own floor ([ADR 063](./063-an-object-store-is-a-service-that-dials.md), [`bench/result/s3.md`](../../bench/result/s3.md)). A `list` adds one URL buffer of `list_url_max` bytes to the calling connection's stack for the life of the connection ([ADR 062](./062-where-a-connection-waits-is-what-it-costs.md)), about 5 KB at the default `key_max` of 512, of which 3 KB is the cursor; a `putMultipart` adds one URL buffer of `part_url_max` (5,027 bytes at the defaults: the key at 3× and an encoded `UploadId` at 3×), with the query written into it in place so no second buffer exists. A `copy` adds one URL buffer of `url_max`, the same as `put`; a `compose` adds `putMultipart`'s `part_url_max` buffer, one part copy at a time. |
| Throughput and p99 | 0 for a handler that never calls S3. For one that does, the floor is a network round trip; signing adds one HMAC-SHA256 ([ADR 060](./060-a-signing-key-changes-once-a-day.md)). Full comparisons against Go and Rust SDKs are in [`bench/result/s3.md`](../../bench/result/s3.md). |
| Binary size | 0 for a program that never imports `nilo_s3`. `s3/listing.zig` and `list` are linked only by a program that names them. |

## Consequences

- **`std.http.Client`'s pool policy is not nilo's**, and that is the price of the zero dependency. Redirect handling, LRU eviction and proxy-environment behaviour are std's; the two places that would have hurt on their own, no ceiling on connections in use and an unbounded drain on `deinit`, are handled through `nilo_fetch`.
- **The version of Zig is part of this module's behaviour** in a way it is not for the rest of nilo, since a change to `std.http.Client` between releases is a change here; the live tests are what find it.
- **`scan.zig` was not moved to the bottom layer by this decision.** It could go cheaply and this was not the caller that justified it; that stays open with no S3 in it.
- **The 24% measurement is the reusable part of this ADR.** The next module that wants to borrow the server's parser should count first: sharing the cheap fifth of a job is not sharing.
- **A decision recorded in one place and implemented in another is a decision that can go missing.** The retry policy was argued and written down here, then handed to `nilo_fetch`'s own ADR under a heading ("no retries") about a different case, and nothing noticed for two releases because the failure needs an idle period to appear and every test dialled a server it had just started. A benchmark against an idle pool is what found it, which is the argument for a run in [`bench/result/`](../../bench/README.md) existing at all.
- `COPY` shipped last, as `copy` and `compose`, on the completion-body check `putMultipart` had already paid for; `docs/todo.md` lost each entry when its call shipped. What is still not built is a `list` that follows its own cursor.
