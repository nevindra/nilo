# A migration is a diff against a snapshot, not a database

**Status:** accepted
**Topic:** [sql-migrations](../design/sql-migrations.md). What the marker may say about a table is its own decision, [ADR 181](./181-the-marker-has-two-kinds-of-word.md); this one is what a migration is, how a version is written and how it reaches a database.

## Context

`nilo_sql` had half a migration tool before it had one. `schema.compare` read the catalog through a Dialect's `introspect`, knew which column types each Zig type may be read out of, and reported a column that was missing, wrongly typed or wrongly nullable. It could not look the other way, at a column the table has and the Row dropped, and `dialect.accepts` answers with the **list** a column may be read out of where `CREATE TABLE` needs the one to write.

What a caller did meanwhile was on file. `stress/arsip` created its one table in ten lines: a second `Db` on the same file, `nilo_start` by hand, the DDL through `db.raw` with the Row of the table being created passed to something that answers no rows. The same table declared `id INTEGER PRIMARY KEY AUTOINCREMENT`, which SQLite reports as nullable while `id: i64` is not, and forty tests passed against it in both optimize modes because a suite that never listens never runs `db.checking`.

A 59-table program was then ported onto the tool over several rounds, and [`docs/input_from_nodeflux.md`](../input_from_nodeflux.md) is what it reported. The version file's shape, `--baseline`, the rule for an older snapshot and the `.sql` twin below are each an answer to one of its findings.

## Decision

**A migration is generated by diffing the program's `sql.Schema` against a snapshot the repository holds. The database is not consulted, and `generate` opens no connection anywhere.**

### Two records, because there are two questions

Most tools keep one and get confused where the two disagree.

| Record | Where it lives | The question it answers |
|---|---|---|
| `nilo_migrations` | in the database | which versions are applied **here** |
| `migrations/snapshot.zon` | in git | what the last `generate` believed the schema was |

The snapshot is what makes `generate` need no database, no shadow copy of one, and no `DATABASE_URL`. It also gives two branches a real answer: two branches that each generate version 8 against the same parent conflict in git, in `snapshot.zon` and in the manifest, and `check` fails naming both. Writing the second one again on top of the merged snapshot is done by hand; a `rebase` command that does it is not built.

Integrity is a hash per version over its own steps plus its parent's hash, so editing a version that has already been applied moves every hash after it and is a red build rather than a surprise in production.

### A rename is written in the type

A diff cannot tell a rename from a drop and an add. The Row says which it was:

```zig
pub const nilo_table = .{
    .name = "users",
    .key = .id,
    .was = .{ .email = "e_mail" },
};
```

`generate` writes `ALTER TABLE "users" RENAME COLUMN "e_mail" TO "email"`, and only while the snapshot still has `e_mail`; once it does not, the tool says the entry is spent and can be deleted. A `.was` naming a column the Row does not have is a Refusal.

### A version is a list of steps, and one Zig file holds it

A data migration cannot be derived from a struct diff and is not attempted. So a version is a list, and a step written by hand sits in the list beside the generated ones, all applied in order inside one transaction. That is what makes expand and contract expressible, which `up`/`down` cannot: the data step sits **between** two DDL steps, and a pair has nowhere to put it.

A version file is four declarations, and `generate` writes one of them:

```zig
const migrate = @import("nilo_sql").migrate;

/// Steps of your own that run *before* the generated ones: the extension a
/// generated column's type comes from, a function a default calls.
pub const before: []const migrate.Step = &.{};

/// And the ones that run after: a backfill, a seed row, a `create_hypertable`.
pub const after: []const migrate.Step = &.{};

pub const version: migrate.Version = .{
    .number = 1,
    .name = "schema",
    .steps = before ++ generated ++ after,
};

// nilo:generated begin
const generated: []const migrate.Step = &.{ … };
// nilo:generated end
```

Each step carries its kind, a `why`, its SQL and a `destructive` flag, so a reviewer reads one file rather than a manifest and a directory. Three things about the layout are decisions rather than formatting:

- **The generated block is at the bottom.** A ported schema puts four thousand lines of `CREATE TABLE` in this file, and a `version` underneath them is a `version` nobody sees.
- **There is a `before` as well as an `after`.** A `CREATE EXTENSION citext` has to run before the column whose type comes from it.
- **The block is delimited by two whole-line markers.** A regenerate replaces what is between them and keeps every byte outside. A file that has lost a marker is **refused**, not rewritten: the only other reading of it is "all of it is generated", and acting on that throws somebody's hand-written steps away and reports success.

**The file carries no hash.** A hash a caller can fill in is a hash a caller can fill in wrong. `migrate.chainOf` walks the list once and is the only thing that computes one, and the `Chain` it hands back is what `applyPending` and `drift` take. The hash is over the SQL, so a reviewer reformatting the file changes nothing.

**One Zig file per version rather than `.sql` files, and the reason is the statement boundary.** Every statement this module sends is prepared ([ADR 051](./051-a-statement-that-is-a-constant-can-be-prepared-once.md)) and a prepared statement is one statement, so a `.sql` file holding three would have to be split. Splitting on `;` is wrong for real SQL (a semicolon inside a string or a `$$…$$` body is not a boundary), so it needs a lexer, and a leaky lexer fails in the worst shape available: `sqlite3_exec` runs several statements happily and the Postgres extended protocol does not, so it passes on a laptop and fails in production. Here the boundary is an array element and nothing is parsed.

`migrations/manifest.zig` is what the tool imports and what `generate` writes, so it has to exist before the first build: seven lines written once (`head` at 0, an empty list, the `chain` function), the tool's from then on. A build step that walks the directory would remove them and the merge conflict two branches get there, and adds a build-time API every dependent calls; not built.

**A step that runs Zig rather than SQL is not expressible.** `Step.sql` is text with nowhere to put a function, and re-hashing every password with `nilo_pw` is the case that wants it. The shape it needs is a `Version` whose pieces are a comptime tuple of steps and functions; not built.

### Re-deriving version 1 is a flag, `--baseline`

Porting a schema is not "add a column"; it is the first version written and checked against a reference over and over. The second `generate` diffs against the snapshot the first one wrote and says "nothing to do", so re-deriving used to mean deleting the snapshot and the version file and resetting the manifest by hand, dozens of times.

`db generate --name schema --baseline` ignores `snapshot.zon` (it does not even read it), diffs the Schema against nothing, rewrites the generated block of version 1 where it stands, and rewrites the manifest and snapshot to match, so `db check` straight after is green. It is the only thing in the module that writes over a file already there, and it refuses in three places, each naming the file:

- **A version it is not re-deriving is in the directory.** Version 2 is a diff against what version 1 left, so a re-derived version 1 leaves it describing a schema nothing ever had.
- **`--name` disagrees with version 1 on disk.** Two version-1 files is a directory `read` refuses, and not one the tool can undo.
- **The file has no generated block.** As above.

### A snapshot an older nilo wrote is still read

Every word the marker gains arrives as a snapshot field with a default, and `std.zon` fills a missing field from its default, so an older snapshot parses as the schema it described. A **renamed** field is the one change without that property; the snapshot has had one, a foreign key's `.column`/`.target` becoming the lists `.columns`/`.targets`.

**A snapshot in an older shape is read through a mirror struct, upgraded in memory and diffed against.** `snapshot.parseWith` tries the current shape first and the older one second, and reports which through `Origin` (`current` or `upgraded`). `generate` and `check` print one line when it was upgraded, and the next `generate` writes the current shape. Nobody has to do anything.

**One mirror struct per shape that renamed a field, kept until 1.0.** That makes the bar visible: a rename costs a struct that lives for the life of the format, and a new field with a default costs nothing.

A parse that fails anyway is printed as `std.zon`'s own sentence with the line and column, not `error.ParseZon` and a stack: the command line reads the directory a second time with a `Diagnostics` of its own.

### Forward only

There is no `down`. A generated one is a lie for anything destructive, the data is already gone, and a script nobody has ever run is the worst thing to reach for during an incident.

**`generate` refuses a destructive step until the caller names it**: `--drop orders.note,notes,extension:pgcrypto`, a column as `table.column`, a table by its name, an extension with `extension:` in front. The refusal prints every loss beside its statement and then the whole command with the names filled in, so what gets typed is what was read. A name that matches nothing holds the version back too, because it is usually a typo for the drop that was meant. The names go in a line at the top of the generated file, and `.destructive = true` stays on each step, so a reviewer sees both.

Destructive means a table, a column or an extension dropped, and **a column type that does not widen**. The widenings are a short list: a wider integer, `float4` to `float8`, an integer or a bounded `numeric` into a wider or unbounded one, a `varchar` into `text` or a longer `varchar`. Anything else can refuse the rows already there, which is loud, or convert them, which is not: `numeric(10,2)` to `numeric(10,1)` rounds every row, `float8` to `float4` drops digits, `timestamptz` to `timestamp` moves every value by the server's zone. The statement carries no `USING`, so a type Postgres will not cast on its own still fails and asks for a step.

A step flagged `needs_backfill` says what it wants for its kind. An added required column cannot be filled by a step in front of it, because it does not exist yet: it wants a `.default` in the marker, or to ship optional first and be made required a version later. A `NOT NULL` or a check that the rows break wants a `.kind = .data` step in `before`.

The honest argument for `down` is the local loop, and its answer is two commands: `reset`, which drops the objects nilo owns and replays from zero, and `squash`, which folds applied history into one baseline. **Neither is built**; they are the debt forward-only creates, and the roadmap holds them. `--baseline` is not `reset`: it touches three files and no database.

### Applying: in process, and the binary knows its version

`migrate.applyPending` runs in the boot phase, `app.before(f, args)`, which `listen()` runs on the services' loop after they start and before it takes a socket ([ADR 180](./180-work-that-needs-the-services-runs-on-their-loop.md)). That is what a SQLite program needs because there is no server to have run the DDL elsewhere. It makes the ledger if it is not there, reads the applied set in one round trip, applies each version in its own transaction, and takes one advisory lock (`pg_advisory_xact_lock`) inside the transaction, because the in-process path is exactly the case where ten replicas boot at once. The ledger's `CREATE TABLE IF NOT EXISTS` runs behind the same lock: two sessions creating the same new table at once can both pass the "not there" check, and the second fails on the catalog's unique index.

**A version the ledger has under another hash stops the run before anything is applied** (`Error.SchemaDrift`). The versions after an edited one were written against what it used to say. `db migrate` has always refused this; a program migrating itself at boot applied on top of it until the one read of the ledger started answering both questions. A version already recorded is skipped without a transaction, so a boot with nothing to do costs that one read.

**On SQLite each version runs with foreign keys off, and checked once before its COMMIT** (`wire.Begin.rebuilding`). SQLite changes a column by rebuilding the table: create the new one, copy the rows, drop the old one, rename. With foreign keys on, that drop deletes the old table's rows first, and every `ON DELETE CASCADE` pointing at it fires inside the version's own transaction. The children are gone and the COMMIT keeps it. The pragma does nothing inside a transaction, so it is an option on the `BEGIN`; `PRAGMA foreign_key_check` finding a row that points at nothing answers `error.ForeignKeyViolated` and rolls the version back. The `.sql` twin for SQLite carries the same pragmas around its `BEGIN` and `COMMIT`.

The manifest holds the version list as comptime constants, so a server has its expected version as a number inside the binary, and one query at boot (`migrate.expect`) says whether the database agrees:

```
error: nilo_sql: this binary was built for schema version 9, the database is at 7.
  Not yet applied: 0008_add_tenant, 0009_split_name.
```

Code ahead of its migration is refused. A database ahead of the code is allowed and logged, because that is what expand and contract is for.

### Applying without Zig: a `.sql` twin, written and never read

Authoring a version needs a Zig compiler: the source is a type, the diff runs at comptime and the manifest is a module. Applying one does not have to, and the first database shared with a service in another language, or migrated by somebody who does not ship the binary, needs it not to.

**`db generate` writes a `.sql` twin beside every version file, and `db check` fails when one is stale.** It holds the statements in order with each `why` as a comment, inside `BEGIN`/`COMMIT`, with a `CREATE TABLE IF NOT EXISTS "nilo_migrations"` first and the ledger row last, so a database brought to head by `psql` is one `migrate.expect` serves and `verify` still holds to the hash. `ms` is 0 because nobody timed it.

**It is an output and never an input.** A version written in SQL by somebody else and picked up by nilo has no snapshot behind it, so the next `generate` would diff against a schema that does not describe the database.

The twin is written from the compiled `Version`, because the hash is chained and a twin needs the versions before it. For a new version, and for `--baseline` deriving version 1 the first time, it is exact. For `--baseline` rewriting a version 1 that has hand-written steps, the new `before` and `after` are Zig this binary did not compile, so **no twin is written**, the outcome says so, and `check` asks for it after the rebuild. Every run refreshes every twin, including a `generate` with nothing to generate, which is exactly when a stale one is easiest to leave behind.

### Between `createMissing` and a version: `addMissingColumns`

`createMissing` creates what is not there and alters nothing; `applyPending` wants versions, a ledger and the `generate` loop. The commonest SQLite program of all lives between them: a single-file tool that added a field to a Row after its first release.

**`migrate.addMissingColumns(db, scope, schema)` adds one `ALTER TABLE … ADD COLUMN` per field a table lacks, from the same `Desc` the create reads, in one transaction, and answers how many.** The live columns come from `db.liveColumns`, the question `checkSchema` asks. A required column with no default is refused with `error.NeedsBackfill` and nothing is sent: SQLite refuses that `ALTER` outright and Postgres refuses it on a table with rows, so it is not a statement this can send and mean. The log carries the statement and the three ways out (a `.default`, an optional field, or a version). A table that is not there is skipped, and nothing else is touched: a dropped or retyped column is `db.checking`'s to report.

### It lives in `sql/`

A `nilo_migrate` module would import `nilo_sql`, a sibling at the Service layer, which `zig build layering` refuses correctly ([ADR 038](./038-a-module-sits-where-the-loop-puts-it.md)). So the code is `sql/migrate.zig`, `sql/migrations.zig` (the half that touches a disk) and `sql/snapshot.zig`, and the linker drops all of it for a program that names none of it.

It needs one declaration on the Dialect contract, `columnType(T)`, beside `accepts` rather than a rule over it: a Row reading `i32` accepts `int4` and `int8`, and creating one writes `int4`.

## What was rejected

**An interactive prompt for renames**, drizzle-kit's and Django's answer. It moves a decision into somebody's terminal, so the same code produces different migrations for different people and neither answer reaches the pull request.

**Down migrations.** The narrow case where a reversal is correct is real (`CREATE INDEX` reverses exactly, `ADD COLUMN` does while nothing has written to it); the shape that would tell the cases apart is an `undo` refusing a version holding a step it cannot reverse. A mechanism for a case nobody has brought.

**A shadow database**, how Prisma computes a diff. It needs a second database wherever the diff runs, CI and a laptop included; the snapshot answers the same question without one.

**Version files as `.sql`, one statement per file.** No lexer, and a first migration of ten tables at about thirty files.

**Accepting the twin as an input**, so a version can be authored in SQL. Rejected above: a version nilo did not generate has no snapshot behind it.

**`--drop` as a switch**, which is what it was. A switch covers the drop nobody read: a field renamed without `.was` is a dropped column and an added one, and it sat in the same list as the drop that was meant, behind the same flag. Naming each one costs a few words on a command line that already printed them.

**`USING "col"::type` on every type change**, so a change Postgres will not cast on its own goes through. An explicit cast is exactly the conversion that truncates a `varchar` and rounds a `numeric` where the implicit one would have refused; it would have turned the loud failures into quiet ones.

**Reading the ledger per version under the lock**, which is what `applyPending` did. Correct, and a BEGIN, a lock and a COMMIT for every version already applied, at every boot. The check under the lock is still made for a version that is not recorded, because another process may have applied it since the read.

**`PRAGMA defer_foreign_keys` for a SQLite rebuild.** It defers the checks and not the actions, so the cascade still fires on the DROP.

**A `.sql` copy beside the Zig file.** Refused at first as a pair that can drift. The twin is that copy, and what changed is that it drifts visibly: it is an output `check` compares against the Zig, not a second source.

**`status --sql` redirected to a file** in place of the twin. It opens a database to know which versions are waiting, which is the whole problem, and it prints no ledger row, so applying it leaves the next boot refusing a database whose tables are all at head.

**A twin without the ledger row.** Applying it by hand would then be half a job, and the missing half is the one that stops the next boot; the row is the only part of the twin a shell script over `status --sql` could not have made.

**A hash in the version file**, so a twin could be written from the file alone. A hash written beside the statements it covers is decoration, because whoever edits a statement is looking straight at it.

**A twin with an unchained hash when the binary is behind**, which puts a wrong hash in a file people apply by hand. **And `check` regenerating a stale twin**: the command CI runs is the one that writes nothing, and a command that fixes what it inspects is a command whose green build means nothing.

**Letting `--baseline` renumber**, deleting versions 2 and up so it works at any head. What it deletes is the only record of what a deployed database has run. **A `--force-baseline`** is the same thing reached by somebody whose only problem is an older snapshot.

**Calling it `reset`.** `reset` is a database operation; a flag on `generate` keeps two unrelated operations out from behind one word and keeps the refusals in the one place that knows about version files.

**One hand-written slot rather than two.** `after` covered every case the port hit; `before` covers the one it named and did not hit, for one line in a generated file.

**A bare comment as the marker**, like `// ---`: a file that happens to contain one gets spliced in the wrong place. `// nilo:generated begin` is ugly on purpose, and the refusal prints it verbatim. **Parsing the old file's Zig** to find the generated steps means shipping a Zig parser to read a file this module wrote.

**Refusing an older snapshot and telling people to delete it.** The snapshot is the other half of every diff: deleting it at version 7 and running `generate` writes a version 8 that creates every table the database has. **A format version in the snapshot** is a number somebody has to remember to bump, and forgetting is this bug again; trying both shapes needs no bookkeeping. **Writing the upgrade back to disk** makes a command that silently rewrites a committed file; the next `generate` rewrites it anyway, in a diff everybody reads.

**`addMissingColumns` as a `Step` for `applyPending` too.** A step that reads the live schema is a version whose contents depend on the database it runs against, which is what the hash chain refuses; the DDL is already shared, through `ddl.addColumn`. **Sending the `ALTER` for a required column and letting the database refuse** works on an empty table and fails on a full one, which is a program that passes in development and fails at the first customer.

## What it costs

Nothing on any of the four axes ([ADR 017](./017-the-trade-budget-has-four-axes.md)), and that is a fact about the shape rather than a budget met: the tool is a second executable in the caller's repository, not in the process the axes measure.

| Axis | Cost |
|---|---|
| Allocations per request | 0 |
| Memory per idle connection | 0 |
| Throughput and p99 | 0 |
| Binary size, a server that does not apply migrations | 0 bytes, measured |

The size row is measured every time this module grew: `zig build size-sql` builds two stripped `ReleaseFast` programs that import `nilo_sql` and never name `migrate`, and both come out byte for byte identical to the same programs built from the commit before ([`bench/result/sql.md`](../../bench/result/sql.md)). **What a server that calls `applyPending` pays has no number yet**; it goes beside the write half's in `bench/result/sql.md` when somebody takes it.

`generate` and `check` touch no database and no network, so their cost is reading the snapshot and the version files, and they are the pair CI runs on every pull request. The twin costs roughly its version file again on disk, committed. Postgres 14 is the floor, because `createMissing` uses `CREATE OR REPLACE TRIGGER` ([ADR 181](./181-the-marker-has-two-kinds-of-word.md)).

Every failure in this ADR is a file or a command line rather than a program, so none of it is a Refusal; the wording is held by tests calling the free functions `sql/cli.zig` prints them with (`writeBaselineRefusal`, `writeSnapshotRefusal`, `writeStale`, `writeTwins`), and **those tests go through `generate`, not through `parse`**, because a test one layer under the path a person takes stays green while nobody can reach the behaviour ([`docs/history.md`](../history.md)). `sql/migrate_live.zig` applies a twin to a real SQLite database and then asks `migrate.expect` and `checkSchema` about it, and widens a table through `addMissingColumns` on both Wires.
