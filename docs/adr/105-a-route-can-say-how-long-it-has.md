# A route can say how long it has

**Status:** accepted
**Topic:** [deadlines](../design/deadlines.md)

## Context

[ADR 022](022-a-deadline-belongs-to-an-operation-not-to-a-request.md) gave the Engine several deadlines, and every one of them bounds an *operation*: a head, one read of a body, one write, a gap between requests. None of them bounds the **request**. A handler that reads a body slowly, calls two services and writes a large response is inside all of them all afternoon. Fiber has a `timeout` middleware and Gin has the request context; nilo had `block_warning_ms`, which only ever logs ([ADR 013](013-handlers-must-not-block-the-thread.md)).

Reading [dusty](https://github.com/lalinsky/dusty)'s `ServerConfig.timeout.request`, one number, 30 seconds, on by default, against nilo's route-level deadline surfaced a second gap. The per-route mechanism answers "what is the right budget for this route", and the question a deployment actually has is **which routes have no budget at all**, the answer being every route whose author did not think about it, which in an application of forty routes is most of them. A route with no deadline is not a route that chose "unbounded", it is a route nobody looked at.

## Decision

```zig
try app.with(nilo.deadline(2000)).get("/report", buildReport);
```

**`Deadlines.set` is the one clamp, and every `arm*` goes through it**: a limit is whichever of the two comes first, and `none` ("as long as it takes", what an idle connection and a WebSocket ask for) becomes the deadline itself. Nothing has to be remembered at the call sites, and a wait added later gets the deadline without anybody wiring it up. The clamp only ever shortens: a deadline that lengthened a limit would loosen the server's own protection against a slow client.

**The write limit is clamped at the moment the answer is written, not when the deadline is set.** `listen()`'s `write_timeout_ms` is a per-write limit that the connection arms before any route has run, and a limit armed there never saw a deadline a route set afterwards: a route with `nilo.deadline(2000)` answering a large body to a client that had stopped reading ran for the thirty seconds of `write_timeout_ms` a write, and a client taking a byte a write for far longer. So `Ctx.armWriteLimit` re-arms it where the answer or a takeover is about to write (`send`, `sendFile`, and `tookOver`, which is `stream`, `events`, `upgrade` and `bodyStream`), through `Deadlines.armWrite`, and `serve.handleConnection` arms it again before every request so a deadline's effect never reaches the next request on the connection. The rule is one case wide on purpose. **When what is left of the deadline is no more than `write_timeout_ms`**, or the write limit is off, the write is bounded by the deadline itself, as an absolute time. **When more is left, the write keeps its per-write limit**, because the engine holds one timeout and it is either a duration for each write or a time for all of them: the absolute time would turn a per-write limit into a limit on the whole response, and cut a 100 MB download at `write_timeout_ms` that a client was taking steadily. What a deadline further off than `write_timeout_ms` therefore does not catch is a client that takes something every `write_timeout_ms` for longer than the deadline; the per-write limit still catches the client that stops. **A deadline that has already passed changes nothing**, so the 503 naming the budget and a handler's late answer still go out, under the ordinary limit. A request with no deadline pays nothing: `armWriteLimit` returns on `until_ns == 0`, and the per-request re-arm is a field store through the vtable the connection already holds.

### A running handler is not interrupted, and deliberately is not

This is the half worth being plain about, because it is what Fiber's middleware does and this does not. Fiber runs the handler in a goroutine and abandons it; Zig has no runtime to abandon it into, and the alternative, cancelling the fiber, is a cancel that **every** handler, every `nilo.Mutex`, every `nilo.sleep` and every Service would have to survive at every line, and [ADR 082](082-a-cleanup-path-is-not-cancellable.md) has already had to carve the cleanup path out of cancellation once, for a narrower case.

So what this catches is the two shapes a request actually overruns in: a client that is slow, on either side (the read and the write are clamped), and a response that is large (the stream's pieces are clamped one at a time, and the deadline is what ends the sequence). The third, a handler doing its own work, is handed to the handler as a question:

```zig
while (try rows.next()) |row| {
    if (c.overdue()) return fail.status(503, "too many rows to do in time", .{});
    try out.json(row);
}
```

`c.timeLeftMs()` is the same answer as a number. Both answer safely on a route with no deadline: `overdue()` is false and `timeLeftMs()` is null, so asking does not require knowing what the route was registered with.

### The calls a route makes inherit what it has left

**A call that leaves the process takes the shorter of its own bound and the time the route has left**, so `deadline(2000)` on a route is also two seconds on the `nilo_fetch` request, the `nilo_s3` object and the `nilo_sql` statement it makes, which Go's `context.WithTimeout` does by carrying the context into `QueryContext` and `NewRequestWithContext`. The Scope carries it ([ADR 144](144-a-scope-that-crosses-a-function-pointer.md)): a Scope that declares `timeLeftMs() ?u32` has a deadline, `Ctx` does, and `core.within(scope, own_ms)` is the shorter of the two, resolved while compiling, so a `nilo.Run` or an `AnyScope` (no declaration) gets its own bound back untouched and pays nothing. A duration rather than an instant, so the toolkit shares no clock with the Engine.

- **`nilo_fetch`**: `Exchange.begin` narrows `timeout_ms` (zero, no limit, becomes the route's time), so a download with no ceiling and only a stall bound is still ended by the route's deadline. The error is the call's own `error.TimedOut`; the route's time running out is a timeout of the call. `nilo_s3` passes the same field at all twelve of its requests and gets it through fetch ([ADR 063](063-an-object-store-is-a-service-that-dials.md)). The credential source's own `fetch_timeout_ms` is not narrowed: it is the store's, shared by requests.
- **`nilo_sql`**: `db.exec`, `db.begin`, `db.stream` and every select, raw statement and relation load run the Wire call under a `core.Limits.Bound` for the time left (`db.zig`'s `bounded`), so the wait for a pool connection or for the SQLite writer and the statement's own socket read, up to the call returning, end at the route's deadline with `error.TimedOut`. Nothing is sent to the server: no `SET statement_timeout` (a round trip per call), no cancel request, so Postgres goes on with a statement until it finds its socket closed, and a connection cancelled mid-statement is closed rather than reused. A statement inside a transaction is armed the same way, from what the route has left at that statement; `commit` and `rollback` are not, because a cleanup path is not cancellable ([ADR 082](082-a-cleanup-path-is-not-cancellable.md)). **The connection is never handed on out of step**: pg.zig's `Pool.release` replaces a connection that is not idle, `Wire.drain` leaves it non-idle when its read is cancelled, and `begin`/`exec` release through the same path, so a cancelled statement costs a redial and nothing else; a SQLite statement is not interrupted (the thread running it finishes it before the fiber hears of the cancellation), so its connection is reset as after any statement. **The cancellation the timer delivered is spent once, by the caller of the Wire**: the Wire hands a cancellation back with `Io.recancel` (ADR 223), `Bound.fired` spends only the timer's own count, so without more the re-armed error stayed on the fiber and the next call, with no deadline, got `error.Canceled` and zio's `recancel` assertion fired (found by the Postgres test). `armed` takes the Bound off with `Bound.finish`, and when it fired drains the pending errors with `Io.checkCancel`; when it did not, a cancellation is somebody else's and is left as the Wire returned it. **zio exposes no count of what an auto-cancel owns and `recancel` asserts when nothing is cancelled**, so "drain, then put one back if a shutdown is in force" cannot be asked; what holds is that `finish` answers true only when no user cancel was in force (zio gives it priority), so a shutdown already under way is never drained. The one window left is a shutdown landing between `finish` and the drain loop, a few instructions wide; closing it wants zio's `AutoCancel.check` to clear what it accounts for. **Only the cancellation becomes `TimedOut`**: a success stays a success, and a real answer (a unique violation, a syntax error, with its Problem) comes back as itself even if the timer fired after it; the Wire's own cancellation shows as `Disconnected` or `QueryFailed` with no SQLSTATE and the message `Canceled`. **A write cut off by the deadline may still have committed on Postgres** (the server is not told), so a retried request needs an idempotency key. `Ctx.timeLeftMs` rounds up, so a request with any time left reads at least 1 and only a spent deadline reads 0. A test cuts a SQLite call off by the route's deadline and runs the next call on the same `Db` (`sql/deadline.zig`), with a Postgres twin that runs when `DATABASE_URL` is set. Rows read after the call returned (a `db.stream`'s, a select's) are not armed.
- **A request whose time has already passed makes no call**: `TimedOut` before the permit, the dial, the pool or the statement.
- **The wait for a `nilo_fetch` permit (the client-wide gate) is not bounded by the route's deadline** (it queues before any bound is armed, as before), **but it is counted**: the time spent queued is taken off the route's time before the call's bound is armed, and a request with nothing left after the wait is refused with `TimedOut` and never dialled.
- **Not covered**: and `tx.deadline` stays Postgres's own server-side `statement_timeout` ([ADR 043](043-a-deadline-needs-a-connection-you-hold.md)).

### What happens when it runs out

A handler that fails while overdue, with nothing sent, gets a 503 naming the budget rather than whatever the failed read or write happened to raise, which is a status an operator can act on. A handler that fails while overdue after sending is left alone: a half-sent response cannot be taken back and turned into a 503. A handler that finishes late without noticing still answers, and the lateness is a `std.log.warn`: the answer on the wire is correct, what is over budget is the route or the work in it, and throwing away work that is already done would be the worse of the two.

### `listen()` sets the floor every request starts with

**`listen()` takes `request_deadline_ms`, the deadline every request starts with**, applied before the middleware chain runs, through the same `until_ns` above, so a route's own `with(nilo.deadline(ms))` replaces it: the route's number is set later and wins, and everything above still holds (every wait is clamped to it, `c.overdue()` and `c.timeLeftMs()` read it, a handler that is running rather than waiting is not interrupted). A request that arrived with an earlier deadline of its own keeps it rather than having the floor lengthen it: a gRPC call's `grpc-timeout` is the client's own number, and a default is not a reason to wait longer than the client will.

**A request that takes the connection over lets the default go.** `c.stream()`, `c.events()`, `c.upgrade()` and `c.bodyStream()` are the four ways a request stops being one that answers and goes, and they are the four where "an upload and a health check do not have the same budget" is exactly right: a default chosen for the health check would cut an event stream off at the same second every time. So a **default** deadline is dropped at the takeover, and a deadline the route asked for **by name** is kept, because that route knew it was going to stream and said thirty seconds anyway. The distinction is one flag on `Ctx`, `_deadline_default`, set by `giveDefaultDeadline` and cleared by `giveDeadline`; the three call sites that used to set the takeover flag by hand now go through one function, `tookOver`, so the rule cannot be forgotten at a fourth.

**Zero, off, is the default.** dusty's thirty seconds is a reasonable number for an API and the wrong number for a report, and the operation deadlines already answer the case ADR 022 was written for, a client that stalls. What is left is a policy about the handlers behind the server, which their author is the one to set; the option's doc comment says thirty seconds is where to start.

## What was rejected

**The write limit armed once for the connection and left alone**, which is what shipped first and what this ADR said the clamp covered. It did not: `giveDeadline` stored `until_ns` and no one re-armed the write clock, so the deadline reached every read and never the write. A live test with a client that reads nothing found it (`a route deadline shortens the write to a client that reads nothing`, 200 ms against a 30,000 ms write limit).

**Always the deadline as an absolute time on the write.** One rule instead of two, and exact for the slow-trickle client. Rejected because the Engine holds one timeout per side, so it replaces the per-write limit with a limit on the whole response: a route with a minute to give would cut a large answer to a steady client at `write_timeout_ms`. A deadline further off than the write limit is left to the per-write limit, and the doc comment on `Deadlines.armWrite` says so.

**Cancelling the fiber.** Above.

**Passing `c.timeLeftMs()` by hand to every outbound call**, which is what this said a handler with a budget to hand somebody else should do. Nothing read it: `deadline(2000)` on a route left the upstream call its own thirty seconds, the memory of a migrant from a framework whose context carries the deadline into every call, and the repair was a line at every call site that nobody has all of. The Scope already crosses into the toolkit (ADR 144), so the shorter bound is taken where each module already chooses one.

**A deadline instant in the Scope (`deadlineNs`) on a shared clock.** The Engine reads zio's monotonic clock and `nilo_core` reads `CLOCK_MONOTONIC` itself, and the two agree on Linux, but a toolkit that must agree with an Engine it may not name is a coupling to keep true on every platform. Time left in milliseconds, which `Ctx.timeLeftMs` already answered, needs no agreement.

**A `request_timeout_ms` in `listen()`, one number for every route, full stop.** The first position, on the grounds that an upload and a health check do not have the same budget and a number loose enough for the slowest route bounds none of the others. That argument stands, and it is why the floor that shipped is one a route's own `nilo.deadline(ms)` replaces and a takeover lets go of, rather than the single non-overridable number this rejected. What was wrong was concluding from it that no floor should exist: the gap was never "what is the right budget for this route", it was "which routes have none at all", and the stress application's forty routes made that concrete, most bounded by nothing because nobody had looked, not because unbounded was chosen ([ADR 099](099-a-route-can-say-what-covers-it.md)).

**Thirty seconds on by default**, dusty's own shape. Refused for the same reason a total was refused above: a default that cuts a first user's report route off at thirty seconds with a 408 they did not configure is a worse first day than one where nothing is bounded and `block_warning_ms` says so. The four operation deadlines already hold the line against a hostile client; what a default-on total would add is a policy about the handlers behind the server, which is the application's to set.

**Keeping the default deadline through a takeover and letting the route re-arm it**, dusty's own shape (`req.setTimeout(...)` before each WebSocket message). Puts the rule in every streaming handler instead of in one place; a handler that forgets is a WebSocket cut off at thirty seconds. Dropping the default at the takeover puts the decision where the takeover is.

**A separate `stream_deadline_ms`**, a second number for the routes the first is dropped from. A route that wants one already has `nilo.deadline`, kept, which is one number in one place rather than two in `listen()`.

**Refusing the request at the start of every framework call once overdue**: `c.send` returning an error because the clock ran out. Turns a correct response that was late into no response at all, and puts a branch on the hottest path in the framework for a case that is rare.

**A deadline that also covers `nilo.sleep` and `nilo.Mutex.lock`.** They park and would honour one, and it is the obvious next step. Not here because the two of them return `error.Canceled` today and a caller cannot tell a shutdown from a deadline apart by that name, which wants a second error and a pass over every handler that catches the first. Worth doing; worth doing on purpose.

## What it costs

| Axis | Cost |
|---|---|
| Allocations per request | None, including the calls: `core.within` and `timeLeftOf` are arithmetic. |
| Memory per idle connection | Nothing held: re-arming the write clock is stores into the Engine's `Clocks`, which the connection already holds, and `armWriteLimit` has no local of its own. None for a route with no deadline: `until_ns` is zero and `clamped` returns its argument on the first line. `Deadlines` carries one `u64` and the `_deadline_default` flag lives on the `Ctx`, which is on the fiber's frame and unwound before the connection waits ([ADR 062](062-where-a-connection-waits-is-what-it-costs.md)). |
| Throughput and p99 | For a route with a deadline: one comparison and, on the `within_ms` arm, one clock read per limit armed (per body read and per write), next to a syscall already there. One `monotonicNanos()` per request when `request_deadline_ms` is set (the same read `block_warning_ms` already makes), none when it is zero. |
| Stack of a request that queries | None for a route with no deadline: `bounded` branches at run time on `timeLeftMs() == null` into the plain call, and the 192-byte `core.Limits.Bound` lives in `armed`, a function that is never inlined, so its frame exists only while a deadline is armed. A route with one touches those 192 bytes plus a call frame, a high-water mark kept for the life of the connection (ADR 062); not measured with `bench/mem.py`. Fetch and S3 add no local, only a `?u32` field in `Begin`. |
| Binary size | `deadline.with` is generic on `ms`, so a program that never calls it links none of it; `giveDefaultDeadline` and `tookOver` are two small functions. |

**Nothing here tells a handler its client has gone**, which is the other half of the gap this ADR answers and is not simply unbuilt: the obvious implementation is wrong. A read-side EOF is *not* "the client left", because a client that sent `Connection: close` and then `shutdown(SHUT_WR)` produces exactly that byte pattern and is still waiting for its response, so answering "peer gone" from it would abandon correct requests. What is real is a write that fails, which a handler already sees; what would be worth building is a signal that separates "the client half-closed and is waiting" from "the socket is gone", and that is a design rather than a call to make. `docs/todo.md` keeps it.
