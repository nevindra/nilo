# GRPC is served over h2c, behind a flag, and HTTP/2 is built only as far as gRPC needs it

**Status:** accepted
**Topic:** grpc
**Extends:** [ADR 027](./027-tls-is-terminated-in-front.md) (gRPC is the one exception to its "HTTP/2 goes with it", and ADR 027 says so)
**Applies:** [ADR 017](./017-the-trade-budget-has-four-axes.md) (what a feature spends, and the number), [ADR 062](./062-where-a-connection-waits-is-what-it-costs.md) (a handler's stack is the connection's), [ADR 066](./066-a-lazy-dependency-is-a-request.md) and [ADR 212](./212-tls-is-an-option-a-build-asks-for.md) (a feature a build asks for, and the default build never hears of), [ADR 213](./213-a-server-answers-on-more-than-one-address.md) (more than one listener), [ADR 105](./105-a-route-can-say-how-long-it-has.md) (a request's deadline)

## Context

ADR 027 refused HTTP/2 and gRPC as a consequence of refusing TLS: browsers speak HTTP/2 only over TLS, negotiated by ALPN, so "no handshake, no ALPN, no HTTP/2, and no gRPC server either, since gRPC is HTTP/2". ADR 212 later let TLS in behind `-Dtls` and said "HTTP/2 does not follow".

**For browsers the derivation still holds, and for gRPC it never did.** gRPC runs over h2c, HTTP/2 in plaintext with prior knowledge, which needs no TLS and no ALPN. That is how it is usually deployed inside a cluster, a mesh, or behind a load balancer that terminates TLS. And the answer ADR 027 gives everything else, a proxy in front, does not reach it: a proxy turns a browser's HTTP/2 into HTTP/1.1 for nothing, but it cannot turn a gRPC call into a request nilo can serve without transcoding against the service's own schema.

**The callers are real and are not ones a nilo user gets to choose.** A service in an organisation whose contract between services is a `.proto` file. A receiver for OTLP, which the OpenTelemetry Collector sends as gRPC by default. A Kubernetes plugin (CSI, CRI, a device plugin), which is gRPC and nothing else. An Envoy external filter (`ext_authz`, `ext_proc`). In each of those the client is somebody else's library, and it speaks HTTP/2.

**What was looked at and does not serve:**

- **Connect and gRPC-Web** run over HTTP/1.1 and would cost the connection nothing. They do not reach a client nilo's user does not own: grpc-go, grpc-js, grpcio, tonic and the Collector all speak HTTP/2 only, and none falls back.
- **A Zig gRPC library.** `ziglana/gRPC-zig` at `ab34a77` was read. Its HPACK has no static table, no Huffman and one-byte lengths; its frames are written little-endian and read big-endian; it has no flow control and routes every call to the first handler. It is a sketch rather than a dependency.
- **A codec of nilo's own, which was refused here and is now built** ([ADR 245](./245-protobuf-is-read-from-the-struct-that-declares-it.md)). [`Arwalk/zig-protobuf`](https://github.com/Arwalk/zig-protobuf) implements proto3, runs Google's conformance suite, and generates service interfaces while stating that it "does not include a gRPC transport layer". The codec was said to be solved and the caller's to bring; the receiver this was written for then wrote one over plain structs instead of generating types, and it moved into nilo as a module the caller imports, which `nilo_http` names only for `app.trace` ([ADR 247](./247-a-request-is-a-span-and-the-trace-leaves-as-otlp.md)), so a build that does not ask for it moves nothing. The transport is what nobody had built.

**The constraint is ADR 017's two hard rows**, and it is the one ADR 212 met: a build that does not ask for gRPC may not move either of them by a byte, and a build that does states what it pays before it ships.

## What was measured before a line was written

In [`bench/result/http.md`](../../bench/result/http.md#what-a-grpc-client-puts-on-the-wire-and-what-a-stream-would-cost), taken with `spike/grpc/` against grpc-go 1.84.0, grpc-js 1.14.5, grpcio 1.84.0, tonic 0.14.6 and the Collector 0.161.0 at its defaults.

**The HPACK table can be zero, and every client measured agrees.** At the default 4,096 bytes a server's decoder keeps what the client inserts, 213 to 420 bytes for a library called by hand, and for the Collector a table that fills: it indexes `grpc-timeout`, a fresh value every call. With `SETTINGS_HEADER_TABLE_SIZE = 0`, all five sent a size update of 0 and kept nothing resident. The price is about 110 bytes more per call inbound and a Huffman decode of every header, which is CPU on the request path and not memory on the idle one: 123 to 125 ns of a 767 to 773 ns call in process once the decoder took two symbols a lookup ([`http.md`](../../bench/result/http.md#two-huffman-symbols-a-lookup)).

**A stream is a fiber, and a fiber is 4,547 bytes plus the stack it touched.** That is what a request in flight on HTTP/1.1 already costs, so the idle figure does not grow with the streams a connection has served. What grows is the worst case of one connection: the cap times that figure, about 1.7 MB at 100 streams of ADR 062's database route, for the calls that are running. A call is collected whole before it runs, and the calls on a connection hold one `max_body` between them, what an HTTP/1.1 connection holds: past that budget a call's window is not topped up, so its client waits on it rather than this side reading. **The budget counts a call until its answer has been written, not until it starts**: a running call still holds its message, the request text built from it, and the inflated copy of a gzip one, all in its arena, and giving the message back at the start let a hundred calls to a slow route hold a hundred messages while the budget said one. The oldest call still arriving is topped up past the budget so that one can always finish, but not while a call that has started still holds bytes, because that one gives them back with nothing more from the client; topping up past it let each call become the oldest in turn and hold a whole message. What a call can hold past the budget is the window it opened with, 64 KiB, so the worst case of messages is two of them and 99 of those windows, about 8.5 MB at the default `max_body` of 1 MB, twice that with the request text each running call builds, about 17 MB. **The answer is held once**, framed over the end of the response it was read from rather than copied, until the client's window lets it go or the write deadline gives up. **A gzip message is inside it too.** Its inflated copy is charged when the call starts, by the size the stream announces in its trailer, **before** it is allocated, and a call whose copy does not fit in what the other calls leave of the budget waits, holding only its compressed bytes, until they give room back; the oldest waiting call starts whatever the room once no started call holds bytes, because nothing else would give any back. A call alone on its connection has all of the budget, so a message of `max_body` still goes through. The charge is released with the call, on every path, because it is part of the call's `held`. The worst case is the budget plus one call's inflated copy and request text, about 3 MB at the default `max_body`, where it was a hundred calls at `max_body` each, about 200 MB. The reading of what that refuses is under [What the budget refuses an OpenTelemetry Collector](#what-the-budget-refuses-an-opentelemetry-collector). Until a review read the code against it, the budget was `max_body` for every call, 100 MB, and a window this side never checked a client against.

**A cap is honoured by queueing, and is not a guarantee.** At a cap of 1 all four libraries queued on the connection, opened no second one and failed no call. tonic, in some runs, sent requests before it had read the server's SETTINGS.

## Decision

**A listener may speak gRPC, over h2c or over TLS with ALPN `h2`, in a build that asked for it, and the default build contains none of it.**

- **A flag, the way TLS is.** A dependent passes `.http2 = true` to `b.dependency("nilo", …)`; in this repository it is `-Dhttp2`. The Engine names the gRPC connection loop only under a comptime `if` on `@import("nilo_build").grpc`, so a build without it links no HTTP/2 code, and a listener that asks for it there is refused at `listen()` with `error.GrpcNotBuilt` and a sentence saying which flag.
- **A listener of its own, not a protocol negotiated per connection.** `.grpc = true` on an `Options.also` entry, or on `Options` itself for a server that speaks nothing else. Every other listener is HTTP/1.1 exactly as before. With `.tls` on the same listener it offers `h2` in ALPN and nothing else, so a client that offers only `http/1.1` fails the handshake rather than reaching a connection that cannot read it; a TLS listener without `.grpc` still offers only `http/1.1`.
- **A method is a route.** `app.post("/package.Service/Method", handler)` registers it, and so does `app.rpc(T)` for every `pub fn` of a struct naming its service ([ADR 258](./258-a-struct-of-typed-functions-is-an-rpc-service.md)), and the handler is an ordinary one: `c.body()` is the message, unframed and inflated, and `c.send(200, "application/grpc", bytes)` is the answer. The connection hands each call to the App as what it read, a `framing.Call` (the method, the path, the metadata as a field block, and the message), through `serve.serveRequest` as an `Arrival.call`, which holds the fields to every rule an HTTP/1.1 head's are held to by the same parser ([ADR 253](./253-an-answer-is-handed-to-the-framing-that-carried-its-request.md)); the answer is collected whole into a `framing.Collected` rather than written as text ([ADR 254](./254-an-answer-can-carry-trailers.md)), then frames it: a 200 is HEADERS, one length-prefixed message (its five-byte prefix written into room collected in front of the body) and `grpc-status: 0` in the trailers; any other status is a Trailers-Only answer. **A failed call's code comes from the error first** (`error.AlreadyExists` is `ALREADY_EXISTS`, `error.RolledBack` is `ABORTED`) and from the status only when the error says nothing (404 is `NOT_FOUND`, 401 `UNAUTHENTICATED`, 503 `UNAVAILABLE`, and so on), one table in `http/code.zig` that a Connect client's failure is named from too ([ADR 257](./257-a-connect-client-is-told-its-failure-in-connect-words.md)); its `grpc-message` is the sentence the failure carried. The call's metadata arrives as request headers, a route's own headers go back as metadata, and its trailers (`c.setTrailer`) go back as trailers. **`grpc-status` and `grpc-message` are set with `c.setTrailer` and refused from `c.setHeader`.** A request is held to RFC 9113 and the gRPC spec before it is a call: a `content-type` that is not `application/grpc` or `application/grpc+` and a subtype (so not `application/grpc-web`) is a 415; a request with a pseudo-header twice, one that is not `:method`, `:scheme`, `:path` or `:authority`, one after a regular field, or no `:scheme`, `:method` or `:path` is a stream error `PROTOCOL_ERROR` (§8.1.1); and a request with both `:authority` and `host` is served with one `host`, `:authority` winning (§8.3.1). Middleware, fail functions, deadlines, counters and the logger see a gRPC call as the request it became, and nothing among them had to learn a word of HTTP/2.
- **A call is answered the way the gRPC documents say.** A message marked compressed with no `grpc-encoding` is `INTERNAL`, and one in an encoding this server does not read is `UNIMPLEMENTED` with `grpc-accept-encoding: identity,gzip`. `expect` in the metadata is not handed to the route, where it had `Ctx` write a 100 head in front of the answer and the call came back `UNKNOWN`. A `grpc-message` trailer the route set itself is what the route put on the wire, encoded already, so only what cannot be sent as it is gets encoded; nilo's own messages are encoded whole.
- **HTTP/2 is built only as far as gRPC needs it.** Frames, HPACK decoding with a table advertised at 0 and an encoder that never indexes, stream states, both flow-control windows, trailers, `RST_STREAM`, `GOAWAY` and `PING`, and `SETTINGS_MAX_CONCURRENT_STREAMS` stated at 100. Not server push, not priorities, not extended CONNECT, not h2c upgrade from HTTP/1.1, and not HTTP/2 for ordinary routes.
- **Unary calls only.** A call carries exactly one message; one with none or two is answered `INTERNAL` with a sentence saying so. Streaming waits for a caller, because a stream held open is the one shape that costs a fiber for its whole life, and every caller above is unary.
- **`grpc-timeout` is the request's deadline** (ADR 105), carried into the App rather than read by the route, and counted from when the call's first HEADERS frame arrived, which is when the client's clock started. `Options.limits.request_deadline_ms` no longer replaces a deadline the request already brought when that one is earlier (`Ctx.giveDefaultDeadline`); a route's own `nilo.deadline` still replaces it, as it replaces the default, because a route that names a number has said what it needs. A route that fails once the client's deadline has passed is answered `DEADLINE_EXCEEDED`, whatever status it failed with, unless it set a `grpc-status` trailer itself. More than eight digits, or a unit that is not one of `HMSmun`, is `INVALID_ARGUMENT`.
- **`grpc-encoding: gzip` is read**, because the Collector sends it on every call by default. Its inflated copy is held to what the connection's budget has left (below). Answers go uncompressed.
- **A hostile client is a test, not a hope.** Rapid reset (CVE-2023-44487) is held by a reset call counting against the cap until its route returns, and the connection sent away past 1,000 refused streams; a CONTINUATION flood by a cap of 64 KiB on one header block; an HPACK header list bomb by counting the list as it decodes and answering `RESOURCE_EXHAUSTED` past 16 KiB; SETTINGS and PING floods by 1,000 frames in a row that move no call forward, which counts PRIORITY, unknown types, empty DATA (to a call collecting its message or not) and CONTINUATION, a WINDOW_UPDATE with nothing being written and a call reset before it ran, and which only a well-formed call reaching dispatch starts again (opening a stream used to, so a HEADERS and an RST every 999 PINGs walked round it, and so did a call refused as malformed); a zero window by the write deadline, counted from when the answer first stuck rather than from the client's last frame, which any frame used to reset; a call that never finishes arriving by the bound a chunked HTTP/1.1 body has, `body_grace_ms` plus `max_body` at `body_min_rate`, its header block included, which sends the connection away with `ENHANCE_YOUR_CALM` because a reset mid-block would leave the table out of step (the silence limit is no bound on a block, since every CONTINUATION resets it), and a connection that owes a call and sends nothing by `body_timeout_ms`; a stream opened after this side's GOAWAY by `REFUSED_STREAM`, so a client that retries it elsewhere does not run it twice; a hundred calls each sent most of the way by the budget above, a call reset while it is still arriving giving its bytes back to that budget at once, and a client that sends past a window it was given, or whose `SETTINGS_INITIAL_WINDOW_SIZE` lifts a send window past 2^31-1 (§6.9.2), by `FLOW_CONTROL_ERROR`, since a window this side does not check is no bound. The HPACK bound counts a field before copying it: copying an entry of the client's table first let one byte stand for 4 KB, 277 MB from a 60 KB block. Each is a test that the client doing it is cut off; the rapid reset and zero window tests were seen to fail with their guard loosened, and the ALPN test with the server offering `http/1.1`. `zig build fuzz -- --frames` throws generated connections at the listener, and `zig build test` replays its corpus.

## What was rejected

**A `content-type` matched with `startsWith("application/grpc")`, a `:scheme` and pseudo-headers nobody checked, two `host` lines, a `grpc-timeout` counted from dispatch, a `control_run` zeroed before a call was validated, and a reset call whose bytes stayed in the budget.** The audit of `http/` at `39896d2` read the bridge against RFC 9113 and the gRPC spec and found each: `application/grpc-web` got a native answer, a duplicate, unknown or late pseudo-header and a missing `:scheme` passed, a client sending both `:authority` and `host` got `INVALID_ARGUMENT` because the translated request carried `host` twice and `http1.zig` refuses that, a call that took its time sending its message got the time it spent sending back, one malformed call in every 999 `PING`s kept the flood cap from ever firing (as did empty `DATA` to a call nothing was collecting), `Conn.onReset` left a dead call's bytes in `collected` so that once the budget was passed only the oldest call was topped up, and a `SETTINGS_INITIAL_WINDOW_SIZE` could lift a send window past 2^31-1 without the `FLOW_CONTROL_ERROR` §6.9.2 asks for. Each is a test now, written to fail first.

**A gzip message inflated to `max_body` whatever the budget had left.** The inflation was charged after it was allocated, so a hundred calls that each announced 1 MB held about 200 MB (their copies and the request text) on a connection whose budget was 1 MB. It is charged before, by the announced size, and held back past the room.

**A call refused `UNAVAILABLE` when its inflated copy did not fit.** It was what shipped first, because it was a few lines and bounded on its own, and the status was chosen so an OTLP exporter would retry rather than drop. Measured against a Collector (below), a retry is not a delay but a cliff: the exporter waits out its backoff, 5 seconds and up, while the server sits idle, so with ten consumers on one connection its queue grew for as long as the load lasted. A call now waits for room instead.

**A call's bytes given back to the budget when it starts, an answer held twice, and a header block bounded only by the silence between its frames.** Found by the same audit and not measured before it was fixed: `dispatch` gave a message back while the running call still held it and two copies, `framed` copied every answer while the response it came from stayed in the arena, and `overdue` skipped a call whose header block was unfinished. Each is a test now, written to fail first.

## What was built differently from the proposal, and why

**The answer was first read back as HTTP/1.1 text.** The App wrote its answer into memory as HTTP/1.1 and `grpc.zig` parsed it back (`parseResponse`, `unchunk`) and framed it over the end of that text (`framedIn`). It shipped unary gRPC without the App knowing HTTP/2, and it lost two things: the error a route failed with, so a duplicate row was `ABORTED` because it was a 409, and any way to set a trailer but a header the parser moved. Since [ADR 254](./254-an-answer-can-carry-trailers.md) the answer is collected by the framing ([ADR 253](./253-an-answer-is-handed-to-the-framing-that-carried-its-request.md)) and none of the three functions exists; a call is 17% faster in process and a `-Dhttp2` build 47,008 bytes smaller.

**The call was first handed to the App as HTTP/1.1 text.** `asRequest` wrote `POST <path> HTTP/1.1`, the metadata, a `content-length` and the message into one buffer, and the App read the head back with `readHead` and `parseHead` as it reads a socket. It needed nothing of the App but the entry it already had, and it cost a copy of the message, a request line nothing read, and a parse of text this file had just written; the field block is all that is left of it, because it is what `Ctx` reads a header from. Since [ADR 253](./253-an-answer-is-handed-to-the-framing-that-carried-its-request.md)'s read half the App takes the call as it was read.

**The proposal had the Engine hand each stream a Reader and a Writer, and a gRPC method be a typed function reading its body through a door (`nilo_read`) that did not exist yet.** Both lost to translation once it was measured. Turning a call into HTTP/1.1 text and back costs 229 ns of a 973 ns call in process (`zig build profile`), which is the whole App's share, parsing included. In exchange nothing under `http/` other than the connection loop knows HTTP/2 exists, the App's core did not grow (`grpc.zig` sits outside `http_core` and reaches the App through `grpc.Host`, four function pointers the App fills in), and every route feature works on a gRPC call on the first day. The typed door came after it, over the translation rather than instead of it: a method whose argument is a `nilo_proto` message reads it from the call's body and answers in protobuf ([ADR 256](./256-a-body-is-read-as-what-its-type-says.md)).

**The proposal's question 5 was whether the only stream open could run on the connection's own fiber, the way an HTTP/1.1 request does.** It cannot, for a reason no benchmark shows: a gRPC client puts every call on one connection, so a call run inline holds every other call, and the connection's own PINGs and window updates, behind it. The live test "two calls at once, the quick one is not held behind the slow one" is what holds it. The price is measured below, and the part of it that is not the fiber is in zio.

## What it costs

Measured on a Ryzen 7 9700X, Linux 7.2.5, Zig 0.16.0, zio v0.18.0; the runs are in [`bench/result/http.md`](../../bench/result/http.md#a-grpc-listener-built).

| axis | default build | a `-Dhttp2` build, HTTP/1.1 listener | a gRPC connection |
|---|---|---|---|
| memory per idle connection | nothing: 5,183 B marginal before and after | nothing: 5,183 B | 5,685 to 5,917 B, converged at 10,000 connections, against 5,322 for HTTP/1.1 on the same binary: under a page more |
| memory per call in flight | n/a | n/a | a fiber, 4,547 B plus the stack the route touched; the cap of 100 times that is one connection's worst case |
| allocations per call | nothing | nothing | 0 from the second call on a connection: a finished call's stream and 4 KiB of its arena are kept for the next. The first call on a connection allocates its stream |
| binary size, stripped `ReleaseFast` | +8 B hello, +112 B rest | +115,720 B hello, +52,432 B rest | the same |
| throughput, unary, h2load `-m 100`, four cores | nothing | nothing | 769k to 774k calls/s at 256 connections, against grpc-go's 589k to 591k and tonic's 902k; 556k to 567k at 1,024, against 578k to 583k and 851k to 856k |
| latency, same runs | nothing | nothing | mean 28 ms at 256 (tonic 27 ms, grpc-go 43 ms), 111 to 113 ms at 1,024 (97 ms, 159 to 163 ms). The worst call was the slowest of the three: 1.4 s at 256, 3.8 s at 1,024, against about 1.1 s for tonic |

h2load reports mean and maximum and no percentiles, so p99 is not on the record; the maximum is quoted because it is the one that is bad.

**The throughput gap is the scheduler, not the protocol.** Run inline on the connection's fiber, which the paragraph above refuses, the same build does 3.12M calls/s at 256 connections and 2.95M at 1,024, at 2.5 µs of CPU a call; with a fiber per call it is 4.4 to 4.7 µs and 0.87 to 0.95 context switches a call. On one executor the fiber costs 2.74 µs against 2.51 inline, so creating it is 0.23 µs. The rest was where zio put it: every `spawn` is dealt round-robin to another executor (`getNextExecutor`) and that executor woken, so nearly every call crossed a thread twice. **A call is therefore spawned on its connection's executor**, `bulkhead.spawnLocal` over zio's `spawnInto(.local)` ([zio#704](https://github.com/lalinsky/zio/issues/704), [zio#761](https://github.com/lalinsky/zio/pull/761)): 2.06 to 2.08M calls/s at 256 connections and 1.61 to 1.63M at 1,024, against 755k and 555k round-robin, with one context switch in thirty calls and the worst call at 52 ms rather than 1.5 s ([`http.md`](../../bench/result/http.md#what-placing-a-grpc-call-on-its-own-executor-buys)). Inline is still 3.12M; the microsecond between them was not run down.

## What the budget does to an OpenTelemetry Collector

**The budget is `max(ceiling + 5, 65,535)`, which is 1,048,581 bytes at the default `max_body` of 1 MiB**, `ceiling` being `max_body` unless a route raised its own with `nilo.maxBody`, and then the largest limit any `POST` route's chain gives ([ADR 156](156-a-route-can-say-how-much-body-it-takes.md)). **A call is collected under its own route's limit**, the raised one or the lowered one, read from the route table as soon as the headers are in, before a byte of the message and before any middleware; the time the client has for it is sized from that limit. A call can never be given more than the ceiling, which is what keeps the budget a bound: a raised route moves what one connection may hold to the largest raise, and nothing else does.  and a call is charged what it holds: the message as it arrived (the compressed bytes), its inflated copy, and the request text built from that copy, so `C + 2B` for a batch of `B` inflated bytes that arrived as `C`. A call starts when `B` fits in the budget less what every other call holds. For `n` calls running side by side that is a budget of at least `(n - 1)(C + 2B) + B`.

**A call that does not fit waits, it is not refused.** Its message is whole, so it holds its `C` compressed bytes and nothing else, in a state of its own (`waiting`), and starts as soon as the calls ahead of it give room back: in order, so a stream of small calls cannot keep a large one waiting, and the oldest whatever the room once no started call holds bytes, so a few waiting calls cannot fill the budget with none able to start. A waiting call is bounded by its `grpc-timeout`, and one whose deadline passes first is answered `DEADLINE_EXCEEDED` (4) without running. To the client it is backpressure with nothing to retry, which is what tonic gives the same Collector through HTTP/2's flow control. A message over `max_body` is still `RESOURCE_EXHAUSTED` (8): it will not fit however long the client waits, and the Collector drops it, which is the caller's `max_body` to fix.

**How many run side by side.** The Collector's OTLP gRPC exporter gzips by default, its `sending_queue` has `num_consumers: 10` and the batch processor `send_batch_size: 8192`, so up to ten batches are on the wire at once on one HTTP/2 connection. Taking a batch as 3 MB inflated and gzip as 8 to 1, `C` is about 0.375 MB and the charge per running call about 6.4 MB:

| `max_body` (= budget) | batches of 3 MB running side by side | the rest of the ten |
|---|---|---|
| 1 MiB (the default) | 0 | refused with `max_body`: a 3 MB batch is over it however many are in flight |
| 4 MiB | 1 | wait |
| 8 MiB | 1 | wait (the second needs 9.4 MB) |
| 16 MiB | 3 | wait |
| about 60 MB | 10 | none wait |

**Measured** ([`bench/result/http.md`](../../bench/result/http.md#what-waiting-for-room-buys-an-opentelemetry-collector)), with the Collector 0.161.0 in front of photon's OTLP spike on nilo, 48 `telemetrygen` workers sending 500-byte logs (batches of about 4.4 MB inflated), `max_body` 16 MiB, for 30 seconds: refused `UNAVAILABLE`, the Collector got 13.7M of 16.3M records through, logged 40 refusals and still had 329 batches queued ten seconds after the load stopped; waiting, it got 22.2M of 22.2M through with no refusal and an empty queue. tonic, the same Collector and load: 19.2M, no refusal, an empty queue. The bound moved by one inflated copy: the oldest waiting call starting past the budget makes the worst case the budget and one call's copies, about 3 MB at the default `max_body`, where a call alone taking the last of the room made it the budget and one request text, about 2 MB.

**The default budget is not changed here.** It is the figure HTTP/1.1 holds, one `max_body`, and a bigger one moves the hard memory axis for every gRPC connection of every caller to serve one whose batch size is a guess. Waiting makes a small budget slow rather than lossy: what it still caps is how many batches run at once per connection, which a budget that is an option would lift for a caller who sizes it from its own batches. That is an entry in [the todo list](../todo.md) under `nilo_http`.

**What the change costs.** Nothing per idle connection: `Conn` stays 392 bytes and `Stream` 368, the count of waiting calls sitting in padding. No allocation: a waiting call keeps the buffer its message arrived in, and its trailer is read once more when it starts, 4 bytes. Binary size: the stripped `ReleaseFast` OTLP spike is 1,179,400 bytes before and after, on macOS, whose Mach-O rounds to 16 KiB, so under a page. Nothing changes for a call that is not gzip, or for one that fits. The frame fuzzer's properties are about what reaches the wire and were not extended; `zig build fuzz -- --frames` held them for 300,000 connections.

## Consequences

- **ADR 027's reasoning is narrowed rather than reversed.** HTTP/2 for browsers and for ordinary routes is still refused, and a proxy is still the answer. What moved is gRPC, because the premise that it needs TLS was never true.
- **One port cannot speak both.** HttpArena's gRPC and h2c profiles put HTTP/1.1 and h2c on one port, or want HTTP/2 for plain GET routes, so nilo enters none of them; that is the listener-of-its-own decision above, kept.
- **The Collector's gzip found a bug that was not gRPC's.** A deflate stream ending in an empty final block, which Go's writer produces on a flush and close, made `encoded.inflate` refuse a body exactly the size it announced. It was as true of an HTTP/1.1 body with `Content-Encoding: gzip`, and is fixed for both.
- **The frame fuzzer found one on its first run.** DATA on a stream already answered or reset drew an `RST_STREAM` every time, which RFC 9113 §5.1 says to ignore and which let a client make the server write a frame for every frame it sent, uncounted. It is ignored now, and the input is in the corpus.
- **The cap is nilo's number, stated, not a library's.** 100 makes a connection's worst case about 1.7 MB of stacks of running calls on a database route, and about 17 MB of messages and the request text built from them at the default `max_body`, and a gzip message's inflated copy is inside that figure too.
- **This is reversible the way ADR 212 is.** The flag off is the build that existed before.
