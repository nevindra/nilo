# Framing

**A request is one thing whatever framing carried it: `Ctx` decides what the answer is, and the framing, HTTP/1.1 or HTTP/2, decides the bytes it leaves in.**

**Guide:** [Requests](../guide/requests.md) · **Reference:** [Ctx](../reference/ctx.md)

The code is `http/framing.zig` (the union, both arms, and `Call`, what an HTTP/2 request is handed to the App as), the eleven places in `ctx.zig`, `serve.zig`, `sendfile.zig` and `stream.zig` that hand an answer to it, `serve.serveRequest`, the one way into the App for either, and `http/h2conn.zig`, the HTTP/2 connection whose calls it collects. This page is where the direction that made a request one thing whatever framing carried it was laid out stage by stage; it has landed, and left the roadmap.

## Overview

```
                    HTTP/1.1 connection                       HTTP/2 connection (-Dhttp2)
                    serve.handleConnection                    grpc.Conn, one fiber a call
                            │                                          │
             head parsed in place, borrowed            call collected, its fields written as a
             from the read buffer (ADR 201)            block in the call's arena; method, path
                            │                          and message handed over as they are
                            │                                          │
             serveRequest(.wire): parseHead         serveRequest(.call): applyTarget, parseFields
                            │                                          │
                            └──────────────► Ctx ◄─────────────────────┘
                                   route, middleware, typed handler
                                              │
                         Ctx._framing: union(enum) { http1, http2 }
                            │                                          │
         status line, Date, Connection,              Collected: status, type, headers,
         Content-Length or chunks, settle,           body, trailers, the failure, copied
         sendfile, 100 Continue, the 101             into the call's arena for the
                                                     connection's fiber to frame
```

## Rules

1. **Nothing above `framing.zig` writes a protocol's bytes.** `Ctx` hands the framing a status, a content type, the headers middleware and the handler set, a body that is whole, streamed or a file, and whether the connection may carry another request; the arm decides the status line, `Connection`, chunking, `settle` and zero-copy. [ADR 253](../adr/253-an-answer-is-handed-to-the-framing-that-carried-its-request.md)
2. **The framing is a tagged union, not a `Ctx` generic over its transport**, so every handler is compiled once and a write costs one compare of a tag. [ADR 253](../adr/253-an-answer-is-handed-to-the-framing-that-carried-its-request.md)
3. **The HTTP/2 arm exists only in a build that asked for HTTP/2 (`-Dhttp2`).** Without `-Dhttp2` its type is `noreturn`, the tag is known while compiling, and the default build pays not even the compare. [ADR 253](../adr/253-an-answer-is-handed-to-the-framing-that-carried-its-request.md), [ADR 220](../adr/220-grpc-is-served-over-h2c-behind-a-flag.md)
4. **The HTTP/1.1 arm writes exactly the bytes `http1.zig` wrote before the seam**, so `behaviour.zig` and `testing.Client`, which read raw HTTP/1.1, are the regression net for it and are not changed by it. [ADR 253](../adr/253-an-answer-is-handed-to-the-framing-that-carried-its-request.md)
5. **The HTTP/2 arm collects an answer whole**, with its trailers and the error it failed with, and copies it into the call's arena; every gRPC call is answered through it, because a call's answer is framed by the connection's fiber after the call's fiber has returned. A stream, a file and a `100 Continue` are not collected yet and are refused by name. [ADR 253](../adr/253-an-answer-is-handed-to-the-framing-that-carried-its-request.md), [ADR 220](../adr/220-grpc-is-served-over-h2c-behind-a-flag.md)
6. **A WebSocket is HTTP/1.1 only, and an event stream handed to the connection is handed to the HTTP/2 connection too.** A WebSocket takes the connection's reader and writer for the rest of its life, which `Framing.wire` gives it, and a multiplexed connection has none to give; on HTTP/2 the handshake is refused with a sentence, and WebSockets over HTTP/2 (RFC 8441) are not served. An event stream fed by Rooms needs only a bell and somewhere to write, so on HTTP/2 the connection writes its posts as `DATA` (stage 6.3). [ADR 253](../adr/253-an-answer-is-handed-to-the-framing-that-carried-its-request.md), [ADR 021](../adr/021-a-websocket-is-a-handler-that-does-not-return.md)
7. **The request head stays a field block, not a list of fields.** `Ctx` reads a header by scanning the head when asked, which is what keeps a request at one allocation; an HTTP/2 call's fields reach it as such a block in the call's arena, a head whose request line is empty, rather than HTTP/1.1 paying for a list. [ADR 253](../adr/253-an-answer-is-handed-to-the-framing-that-carried-its-request.md)
8. **A request enters the App as what its framing read, and nothing is written into a protocol it did not arrive in.** Both enter at `serveRequest`, told how by a `framing.Arrival`: `.wire` for an HTTP/1.1 head still to be read, `.call` for an HTTP/2 `framing.Call`, its method, path, field block and body. Only the head branches on it, and without `-Dhttp2` the `.call` arm is `noreturn`, so the default build pays not even the compare. [ADR 253](../adr/253-an-answer-is-handed-to-the-framing-that-carried-its-request.md)
9. **An HTTP/2 request's fields are held to every rule an HTTP/1.1 head's are, by the same loop.** `http1.parseFields` is `parseHead`'s loop with no request line in front, chosen while compiling, and `http1.applyTarget` holds a method and path to what a request line holds them to; a refusal is the status HTTP/1.1 answers it with, so a call cannot reach a route a request could not. [ADR 253](../adr/253-an-answer-is-handed-to-the-framing-that-carried-its-request.md)
10. **A trailer is one list on `Ctx`, settable until the body ends, on every framing alike.** HTTP/2 sends it after the body; an HTTP/1.1 chunked stream as a trailer section; a whole HTTP/1.1 answer is chunked to carry it only when the request sent `TE: trailers`, and leaves it off otherwise. A name RFC 9110 §6.5.1 bars is refused where it is set, and a route that sets none pays nothing. [ADR 254](../adr/254-an-answer-can-carry-trailers.md)
11. **An answer is written when it is sent, unless a middleware holds it** with `next.hold(c)`, and then when the chain has unwound. A header set after the head was written is refused with a sentence naming `hold`. [ADR 008](../adr/008-middleware-is-an-onion-of-ctx-functions.md)
12. **A framing is told when an answer is a failure, and with which error.** HTTP/1.1 ignores it; gRPC picks its code from the error before the status, because a status alone cannot tell a duplicate row from a lost race. [ADR 254](../adr/254-an-answer-can-carry-trailers.md)
13. **A body is read as what its type says, and a message answers in the spelling it was asked in.** A struct with a `wire` table is read as protobuf when the request's `Content-Type` names it and as JSON under any other label, as every struct is, and answered in the same; a type with `nilo_content_type` and `nilo_decode` is read only under its own label. The spelling is the request's, never `Accept`'s, which is what makes one function a JSON route, a protobuf route and a gRPC method at once. [ADR 256](../adr/256-a-body-is-read-as-what-its-type-says.md)
14. **A Connect call that fails is told so in Connect's words.** A request carrying `Connect-Protocol-Version: 1` gets `{"code","message"}`, the code from the error first and the status otherwise, the one table the gRPC listener reads too; every other request keeps nilo's shape or the App's. Only a program with a message route links it. [ADR 257](../adr/257-a-connect-client-is-told-its-failure-in-connect-words.md)
15. **A struct of typed functions is a service.** `app.rpc(T)` serves each `pub fn` at `/<nilo_service>/<Method>`, the name's first letter upper-cased, as the route `post` would have registered; a `pub fn` that speaks no message is refused. [ADR 258](../adr/258-a-struct-of-typed-functions-is-an-rpc-service.md)

## How the direction is built

The roadmap's direction, in the order each stage depends on the one before it. A stage leaves this list when it lands and the rest keep their numbers, because ADRs and benchmark entries cite them; what a landed stage measured is in its ADR and in [`bench/result/http.md`](../../bench/result/http.md#an-answer-handed-to-the-framing). Stage 1, the answer handed to the framing, is [ADR 253](../adr/253-an-answer-is-handed-to-the-framing-that-carried-its-request.md); stage 2, trailers, a held answer and gRPC answered from the collected arm, is [ADR 254](../adr/254-an-answer-can-carry-trailers.md) and [ADR 008](../adr/008-middleware-is-an-onion-of-ctx-functions.md); stage 3, an HTTP/2 call handed to the App as what was read rather than as HTTP/1.1 text, is ADR 253's read half; stage 4, a codec chosen by the content type, Connect's errors and a struct served as a service, is [ADR 256](../adr/256-a-body-is-read-as-what-its-type-says.md), [ADR 257](../adr/257-a-connect-client-is-told-its-failure-in-connect-words.md) and [ADR 258](../adr/258-a-struct-of-typed-functions-is-an-rpc-service.md).

**Stages 5 to 7 are designed whole** in [ADR 259](../adr/259-http2-is-a-framing-of-every-request.md) and [ADR 260](../adr/260-a-request-on-http2-runs-from-its-headers.md), and built in this order because a browser must not reach HTTP/2 before every route that works for it on HTTP/1.1 works there too. Each step below lands with `zig build test-all` green against live services in both optimize modes, the gRPC frame fuzzer run, its numbers in [`bench/result/http.md`](../../bench/result/http.md) against the tree before it, and its documentation in the same change.

5. **HTTP/2 carries every request, on the port HTTP/1.1 is on** ([ADR 259](../adr/259-http2-is-a-framing-of-every-request.md)).
    - **5.1, the split and the flag.** `grpc.zig` becomes `h2conn.zig`, the connection, and `grpc.zig`, the envelope; `-Dgrpc` and `.grpc = true` become `-Dhttp2` and `.http2 = true`, the old names refused by the build in one line. No behaviour changes: every test passes as it was, and a build without the flag is byte-identical. Landed: a `-Dhttp2` build is about 600 bytes larger than the `-Dgrpc` build, by code the envelope hands back as values ([`bench/result/http.md`](../../bench/result/http.md#what-splitting-the-http2-connection-from-the-grpc-envelope-costs)).
    - **5.2, one port.** Every plain listener of a `-Dhttp2` build reads the first bytes and serves HTTP/2 on the preface and HTTP/1.1 on anything else, decided at the first byte that differs, and the 505 goes. The listener option `.grpc` is left meaning one thing until stage 7 removes it: a TLS listener that offers `h2` alone by ALPN, which is how gRPC over TLS is served until a TLS listener offers both. Held: the HTTP/1.1 idle figure of a `-Dhttp2` build unchanged by `bench/mem.py`, and the routed `GET` inside its spread; a tail call first, the `noinline` hand-on from the first wait where the ABI refuses one. Landed: the choosing is inlined into the Engine's entry with the HTTP/1.1 loop and the HTTP/2 loop run from the entry once it has returned (the tail call compiled and cost a page, the cause being `waitForRequest` losing its inlining, which is named inline now); an HTTP/1.1 connection idles at 5,197 bytes at 10,000 connections as before, a silent one at 5,192, the routed `GET` at 942k requests a second either side, the default build `cmp` equal, and the `-Dhttp2` build 464 bytes under 5.1's and 112 to 144 over `-Dgrpc`'s ([`bench/result/http.md`](../../bench/result/http.md#what-one-port-for-http11-and-http2-costs)).
    - **5.3, any request.** Any method but `CONNECT` on HTTP/2, held to RFC 9113 §8 (pseudo-headers, connection-specific fields, `te`, `content-length` against the `DATA`, `cookie` joined); answered as HTTP (`:status, `content-type`, `content-length`, `date`, the route's headers, `DATA`, trailers; `HEAD` without `DATA`), gRPC as its envelope. `Ctx.connection()` removed. A streamed answer, a file, `bodyStream`, `eventsFrom` and `upgrade` refused by name. Tested by a shared HTTP/2 test client and a list of `behaviour.zig` cases run over both framings with the same status, headers and body expected; outside the suite by `curl --http2-prior-knowledge` and by [h2spec](https://github.com/summerwind/h2spec) against a running server (Docker), its result recorded. Held: allocations per request no more than HTTP/1.1's from the second request on a connection, by a test; the time of a `GET` in process beside HTTP/1.1's in `zig build profile`; the idle figure of an HTTP/2 connection with no call in flight, plain, by `bench/mem.py` taught the preface. Landed: 0 allocations on both framings from the second request; a routed `GET` over HTTP/2 963 to 971 ns in process against 413 on HTTP/1.1 (558 ns of it frames, head and answer, 34 ns HPACK); an idle HTTP/2 connection 9,355 bytes at 10,000, 10,686 with a stream open, the HTTP/1.1 figure unchanged at 5,197; `h2load` 947k to 1,016k requests a second; the default build `cmp` equal and the `-Dhttp2` build 12.7 KB larger. h2spec fails 67 of 146 as shipped, nearly all of them the suite sending no table size update after our table of 0 (RFC 7541 §4.2), and the real violations it showed once the table was widened on a scratch copy are fixed ([`bench/result/http.md`](../../bench/result/http.md#what-any-request-on-http2-costs)).
6. **A request on HTTP/2 runs from its headers, and its body and answer are pipes** ([ADR 260](../adr/260-a-request-on-http2-runs-from-its-headers.md)).
    - **6.1, the inbound pipe.** Dispatch when the header block is whole; the request's reader takes the stream's `DATA` and waits on the connection; the body framed by the transport; `c.body()` handed over uncopied when it arrived whole; `c.bodyStream()` and `100-continue` as on HTTP/1.1; the gRPC envelope reads its prefix and message through the pipe, inflating on the call's fiber under the connection's budget; the wait a primitive of `bulkhead.zig`. Held: the message rows of `zig build profile` within one wait of collected; an upload faster than its handler holds the connection to its budget, by a test. Landed: the pipe is `inbound.zig` and the wait is `bulkhead.Monitor` and `Signal`; the stream's window is given back as the call reads, half a window at a time, and the connection's as bytes arrive; `Expect: 100-continue` is answered at the first read of a body that has not arrived and never for one that has; gRPC reads and inflates on the call's fiber and waits for budget by `Inbox.reserve`; a `content-length` the DATA does not match resets the stream with PROTOCOL_ERROR. An upload faster than its handler held 68 KB while it stalled and 99 KB at the peak of 8 MiB; a build without the flag is `cmp`-identical and a `-Dhttp2` one 14.6 KB larger. **The message rows of `zig build profile` are 62 to 85 ns (7 to 10%) slower in process, where the stage asked for within one wait**, and an idle HTTP/2 connection weighs 70 to 139 bytes more; through a server the wait is not resolved from collected by `h2load` ([`bench/result/http.md`](../../bench/result/http.md#what-a-request-on-http2-costs-when-its-body-is-a-pipe)).
    - **6.2, the outbound pipe.** `streamHead`, `piece`, `end` and `file` on the `.http2` arm, the stream's buffer lent to the connection for the wait and its `DATA` written straight out of it under both windows; a reset or a stuck window waking the call with an error. Held: no allocation per piece, by a test; pieces per second and a file's throughput beside HTTP/1.1's. Landed: a piece allocates nothing (the same count for a stream of 200 as of 1); 15.7 million pieces a second over HTTP/2 against 30 on HTTP/1.1, a 64 MiB file at 3.2 GB/s against `sendfile`'s 6.7 to 7.3; a client that stops reading is reset with `CANCEL` at the write deadline, and the call's next write fails; one connection takes turns between streams, 64 KiB each (a small answer ended after 128 KiB of an 8 MiB one); the default build `cmp` equal, the `-Dhttp2` build 11 KB larger, an idle HTTP/2 connection unchanged to the byte, the profile rows unchanged, one 64 MiB lend at 4.9 GB/s; h2spec 140 to 141 of 146 on a widened table, as the tree before it; the fuzzer found three bugs of the pipe in its first run, now corpus lines ([`bench/result/http.md`](../../bench/result/http.md#what-a-request-on-http2-costs-when-its-answer-is-a-pipe)).
    - **6.3, an event stream handed over.** `eventsFrom` on HTTP/2 hands its rooms to the connection, which writes their posts as `DATA` when it wakes, and the handler's fiber ends; `RoomEvents` split into the step both framings run and the wait only HTTP/1.1's loop does. Held: the idle figure per stream against a fiber's, at 1,000 and 10,000 streams. Landed: the stream's `Http2Events` is the Rooms' bell and the connection's step, run in the same rotation as every other stream under both windows, a stream stuck for the write limit reset with `CANCEL`, the keep-alive comment bounding the connection's wait, the streams ended under a cancellation shield when a stop cancels the connection, and every Room left on RST_STREAM, GOAWAY, connection close and server stop. A handed-over stream weighs 6.2 KB at 10,000 opened a thousand at a time and 12 KB opened at once (unexplained), against 19.6 KB parked; HTTP/1.1's 5,192 and an idle HTTP/2 connection's 9,423 unchanged to the byte; the default build `cmp` equal, the `-Dhttp2` build 5.1 KB larger and 9.8 KB more for a program that calls `eventsFrom`; 15 to 17 million events a second to 100 subscribers over HTTP/2 against 18 million over HTTP/1.1; h2spec 139 to 141 of 146 on a widened table, as the tree before it ([`bench/result/http.md`](../../bench/result/http.md#what-an-event-stream-handed-to-the-http2-connection-costs)).
7. **A browser is offered HTTP/2** (ADR 259, revising [ADR 027](../adr/027-tls-is-terminated-in-front.md) in place). A TLS listener of a `-Dtls -Dhttp2` build offers `h2` and `http/1.1` by ALPN and serves what was chosen, and the listener option `.grpc` goes, through one call chosen after the handshake, its frame measured against ADR 212's page. Before it lands: the idle figure of an HTTP/2 connection over TLS on record, a page load in Chromium over both protocols, a static file over TLS on both, and h2spec over TLS. The deploying guide says what a browser gets and what a WebSocket does. Landed: the handshake offers `h2` then `http/1.1` in a `-Dhttp2` build and `http/1.1` alone in any other, the one TLS entry reads `conn.alpn_protocol` and runs the HTTP/2 connection through the plain listener's `noinline` hand-on, and `.grpc` is removed with Zig's own "no field named" as its refusal (the second TLS entry went, 2.4 to 2.6 KB of a `-Dtls -Dhttp2` binary). Held: an HTTP/1.1 connection over TLS at 9,370 bytes at 10,000 connections against 9,364 before, the marginal cost from 1,000 to 10,000 identical, and a plain listener unchanged to the byte; an HTTP/2 connection over TLS 9,564 to 9,581 after one `GET`; a page of nineteen subresources in Chromium over one connection against four to six, equal on loopback and 77 to 80 ms against 117 to 121 with 20 ms added to every request, Chromium working with a table size of 0, an `EventSource` and a WebSocket completing, the WebSocket as a 101 on a connection of its own; h2spec 142 of 146 over TLS. It found a stall that was not HTTP/2's: a record layer holding the next record sent the connection to wait on an emptied socket (one in a thousand), now `Wake.held`. Two numbers went the wrong way and are in `docs/todo.md`: a held 1 MiB file over TLS is slower on HTTP/2, and a spilled 64 MiB one is 2.6 times slower on HTTP/1.1 ([`bench/result/http.md`](../../bench/result/http.md#what-offering-h2-to-a-browser-costs)).

Stage 6 used to be listed as the roadmap's second direction's. The pipes are this direction's, because a browser cannot be offered HTTP/2 without them; what that direction adds on top of them is the shape a handler writes a stream in, gRPC streams included.

## Decisions

| ADR | What it decides |
|---|---|
| [253](../adr/253-an-answer-is-handed-to-the-framing-that-carried-its-request.md) | `Ctx` hands its answer to a framing, a tagged union whose HTTP/2 arm exists only under `-Dhttp2`, and what that costs the HTTP/1.1 path |
| [254](../adr/254-an-answer-can-carry-trailers.md) | An answer carries trailers on every framing; gRPC answers from the collected arm, with `grpc-status` a trailer and its code taken from the error first |
| [008](../adr/008-middleware-is-an-onion-of-ctx-functions.md) | A middleware changes an answer after `next` by holding it (`next.hold`), and a header set after the head is refused |
| [256](../adr/256-a-body-is-read-as-what-its-type-says.md) | A message is read as JSON or protobuf by the request's content type and answers in the same one; any other type reads its own body with `nilo_decode` under its own label |
| [257](../adr/257-a-connect-client-is-told-its-failure-in-connect-words.md) | A request carrying `Connect-Protocol-Version: 1` that fails is answered `{"code","message"}`, the code from one table with gRPC's, in a program with a message route |
| [258](../adr/258-a-struct-of-typed-functions-is-an-rpc-service.md) | `app.rpc(T)` serves a struct's `pub fn`s as `/<nilo_service>/<Method>`; not `app.service`, which reads as a Service |
| [259](../adr/259-http2-is-a-framing-of-every-request.md) | `-Dhttp2` brings HTTP/2 for every request: every listener answers both, by the first bytes or by ALPN; gRPC is an envelope over it (stages 5 and 7) |
| [260](../adr/260-a-request-on-http2-runs-from-its-headers.md) | A request on HTTP/2 runs from its headers; its body and its answer are pipes between its fiber and the connection's, under the client's windows (stage 6) |
| [285](../adr/285-a-burst-of-http2-answers-leaves-in-writes-of-32-kib.md) | A burst of HTTP/2 answers of 1 to 16 KiB is written into a 32 KiB buffer taken for the burst and given back at the flush, so it leaves in writes of 32 KiB, not one an answer |

## Open questions
