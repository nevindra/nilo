# Changelog

What changed between one tag and the next, not what changed between commits.
This file holds the release that has not been tagged yet;
[the releases page](https://github.com/nevindra/nilo/releases) holds the ones
that have, one page each. What was measured and what was got wrong on the way is
in [`docs/history.md`](./docs/history.md); what is coming is in
[`docs/todo.md`](./docs/todo.md), and what was refused or answered is in
[`docs/decided.md`](./docs/decided.md).

## Unreleased

### Breaking

- **The build flag `grpc` is `http2`: pass `.http2 = true` to `b.dependency("nilo", …)` where you passed `.grpc = true`** (`-Dhttp2` for `-Dgrpc` on a command line). HTTP/2 will serve every request and gRPC rides it, so the flag is named for what it builds ([ADR 259](docs/adr/259-http2-is-a-framing-of-every-request.md)). The old name is refused by the build in one line saying so.
- **The listener option `.grpc` is gone, from `listen()` and from an `also` entry: delete the line** (`.also = &.{.{ .port = 4317, .grpc = true }}` is `.{ .port = 4317 }`). On a plain listener it already did nothing, and on a TLS one it made the handshake offer `h2` alone, which a TLS listener now offers beside `http/1.1` without being asked, so a client that offered only `http/1.1` is served where it failed the handshake. The compiler refuses a program that still sets it with its own "no field named `grpc`" ([ADR 259](docs/adr/259-http2-is-a-framing-of-every-request.md)).
- **`nilo.Stream.init` and `initClosing` take the request's `Framing` where they took the connection's `*std.Io.Writer`.** Both are what `Ctx.stream` builds, and nothing in the reference shows them; a test that built a `Stream` by hand against a buffer builds a `Framing` around that buffer first (`.{ .http1 = .{ .in = &reader, .out = &writer, .minor_version = 1 } }`). Every answer now leaves through the framing that carried its request, which is the first stage of HTTP/2 for more than gRPC ([ADR 253](docs/adr/253-an-answer-is-handed-to-the-framing-that-carried-its-request.md)).
- **A header set after the answer's head was written is refused with an error**, where it used to be dropped without a word. A middleware that set a header after `try next.run(c)` and saw it reach the client never did; it calls `next.hold(c)` instead, or sets the header before `next`, or with `defer c.setHeader(...) catch {};` for one that must cover failures too ([ADR 008](docs/adr/008-middleware-is-an-onion-of-ctx-functions.md)).
- **`c.setHeader("grpc-status", …)` and `c.setHeader("grpc-message", …)` are refused.** Set them with `c.setTrailer`, which works the same on HTTP/2 and HTTP/1.1 ([ADR 254](docs/adr/254-an-answer-can-carry-trailers.md)).
- **A gRPC call that fails with `error.AlreadyExists` answers `ALREADY_EXISTS` (6), and one that fails with `error.RolledBack` answers `ABORTED` (10)**, where they answered `ABORTED` and `UNAVAILABLE` from their HTTP status. A client that retried on those codes sees the right ones now.
- **`App.grpcHost` is a compile error in a build without `-Dhttp2`**, where it compiled and was undefined behaviour in ReleaseFast if reached.
- **The idempotency and cache record encoders take the answer's trailers** beside its headers. A record written before reads the same.
- **`c.connection()` is removed.** It named an HTTP/1.1 `Connection` line, which HTTP/2 does not have. `c.keepAlive()` says whether the connection will carry another request, and is the same on both.
- **On HTTP/2, a request with a `content-type` that is not gRPC is served as HTTP**, where it was a 415. A build with `-Dhttp2` now answers every method but `CONNECT` (a 501) on a plain listener to a client that opens with the HTTP/2 preface.

### Added

- **`c.setTrailer(name, value)`**, a field sent after the body: a HEADERS frame on HTTP/2, a trailer section on a chunked HTTP/1.1 stream, and on a whole HTTP/1.1 answer when the client sent `TE: trailers`. With it `c.trailers()`, `c.clientReadsTrailers()`, `Ctx.checkTrailer`, and `.trailers` on `nilo.Response(T)` and `nilo.Status(code)`. A route that sets none pays nothing ([ADR 254](docs/adr/254-an-answer-can-carry-trailers.md)).
- **`next.hold(c)`**, which hands a middleware the answer below it unwritten as a `nilo.Answer` (`status`, `body`, `setHeader`, `setTrailer`, `replace`), written when the chain has unwound. A body sent with `c.send` under a hold is copied into the arena, free under 16 KiB and costly above it; **`c.sendKept`** sends one that already outlives the chain without the copy ([ADR 008](docs/adr/008-middleware-is-an-onion-of-ctx-functions.md)).
- **A protobuf message is a handler's argument and its answer**: a struct with a `wire` table is read as JSON or protobuf by the request's `Content-Type` and answered in the same, so one function is a JSON route, a protobuf route and a gRPC method, with no `proto.decode` in it. Any other format is read by the type itself with `nilo_content_type` and `nilo_decode`, the mirror of `nilo_write`. The document files a message under both content types ([ADR 256](docs/adr/256-a-body-is-read-as-what-its-type-says.md)).
- **A Connect client is told a failure as the code it reads**: a request carrying `Connect-Protocol-Version: 1` that fails is answered `{"code":"not_found","message":"…"}`, the code from the error first and the status otherwise, the table a gRPC call's code comes from. Every other request keeps nilo's shape or the one `app.failures` named, and a program with no message route links none of it ([ADR 257](docs/adr/257-a-connect-client-is-told-its-failure-in-connect-words.md)).
- **`app.rpc(T)` serves a struct as an RPC service**: `pub const nilo_service = "helloworld.Greeter"` names it, and each `pub fn` is a method at `POST /helloworld.Greeter/SayHello`, its first letter upper-cased, reachable by gRPC, Connect and plain JSON. A `pub fn` that speaks no message, or two that become one method, is a compile error ([ADR 258](docs/adr/258-a-struct-of-typed-functions-is-an-rpc-service.md)).
- **In a `-Dhttp2` build, every plain listener answers HTTP/1.1 and HTTP/2 on the same port**, told apart by the client's first bytes: the 24-byte HTTP/2 preface is HTTP/2 with prior knowledge (what every gRPC client and `curl --http2-prior-knowledge` send), anything else is HTTP/1.1, decided at the first byte that differs, so a short request is never waited on. A gRPC service no longer needs a port of its own, and a client that reached a gRPC listener with HTTP/1.1, which got a 505, is now served.  `Upgrade: h2c` is ignored and the request served as HTTP/1.1. An HTTP/1.1 connection costs what it did (5,197 bytes idle at 10,000 connections, the routed `GET` at 942k requests a second either side), and a build without the flag is byte-identical ([ADR 259](docs/adr/259-http2-is-a-framing-of-every-request.md)). Only gRPC calls are answered on HTTP/2 for now.
- **In a `-Dhttp2` build, HTTP/2 serves any request** (stage 5.3 of [the framing page](docs/design/framing.md)): the router, middleware and handler run as on HTTP/1.1, on a fiber a stream, held to RFC 9113 §8 (pseudo-headers, connection-specific fields, `te`, `content-length` against the `DATA`, `cookie` joined), answered with `:status`, `content-type`, `content-length`, `date`, the route's headers, `DATA` under both windows and trailers, and `HEAD` without `DATA`. `100 Continue` is sent when the handler first reads a body that has not arrived. What still waits is refused by name with a 500 that says so: `c.upgrade` (a WebSocket is HTTP/1.1); the stream, the event stream, the file and `c.eventsFrom` arrive in the entries below. An HTTP/2 request costs 963 to 971 ns in process against 413 for the same `GET` on HTTP/1.1, allocates the same from the second on a connection, and an idle HTTP/2 connection is 9,355 bytes at 10,000 ([`bench/result/http.md`](bench/result/http.md#what-any-request-on-http2-costs)).
- **In a `-Dhttp2` build, a request on HTTP/2 runs when its headers are in, and its body is read through a pipe** (stage 6.1): a handler starts as it does on HTTP/1.1, `c.body()` waits for the whole of it and hands it over where it arrived with no copy and no allocation, **`c.bodyStream()` works on HTTP/2** under its own `max_bytes`, and the client is told it may send more as the handler reads, so an upload faster than its handler holds the connection to one window (68 KB while stalled, 99 KB at the peak of 8 MiB) instead of the connection collecting it. `Expect: 100-continue` is answered when the handler first reads a body that has not arrived, and not when it already has. A gRPC message is read and inflated on the call's own fiber and a gzip one waits for room in the connection's budget there. A `content-length` the DATA does not add up to resets the stream with PROTOCOL_ERROR and fails the read that waits, a client that stops sending is held to the bound a chunked HTTP/1.1 body is, and a reset stream, a GOAWAY or a dead connection wakes a waiting handler with the error a closed socket gives. After a complete answer to a client that is still sending, the connection says RST_STREAM with NO_ERROR (RFC 9113 §8.1). **A handler that never reads its body now runs, and may answer, before the client has finished sending it** (the connection says RST_STREAM with NO_ERROR when it has answered first). Cost: a unary gRPC call is 62 ns and a small JSON `POST` 85 ns slower in process (7 and 10%), and an idle HTTP/2 connection weighs 70 to 139 bytes more; a build without the flag is byte-identical, a `-Dhttp2` one is 14.6 KB larger, and through `h2load` the pipe's wait is inside the spread of the collected one ([`bench/result/http.md`](bench/result/http.md#what-a-request-on-http2-costs-when-its-body-is-a-pipe)).
- **In a `-Dhttp2` build, `c.stream()`, `c.events()` and `c.sendFile` work on HTTP/2** (stage 6.2): a handler writes its answer in pieces as it does on HTTP/1.1, through a pipe the connection empties into `DATA` frames as the client's windows allow, trailers included, `HEAD` as a head with no `DATA`, and a file read into frames a buffer at a time, a range request too (there is no `sendfile` between frames). A piece allocates nothing: the connection writes the frames out of the buffer the call lent. A client that stops reading is reset with `CANCEL` at the write deadline and the call's next write fails, as on a dead HTTP/1.1 socket, and a reset stream, a GOAWAY or a closed connection wakes a call that waits to write; one connection takes turns between its streams, 64 KiB each and in rotation, so a small answer is not held behind a large one and no stream takes every window update, and a file's buffers are held to 1 MiB a connection. `c.upgrade` stays refused by name on HTTP/2. Cost: pieces at about half HTTP/1.1's rate (15.7 against 30 million a second) and a file at 3.2 against `sendfile`'s 6.7 to 7.3 GB/s, an idle HTTP/2 connection unchanged to the byte, and a `-Dhttp2` build 11 KB larger; a build without the flag is byte-identical, and HTTP/1.1, its `sendfile` path and the rows of `zig build profile` are unchanged ([`bench/result/http.md`](bench/result/http.md#what-a-request-on-http2-costs-when-its-answer-is-a-pipe)).
- **In a `-Dhttp2` build, `c.eventsFrom` works on HTTP/2** (stage 6.3): the stream is handed to the connection as on HTTP/1.1. The Rooms ring the connection's bell, the connection writes what was posted as `DATA` under both windows in turn with its other streams, and the handler's fiber has ended, so the stream holds no handler and a connection of event streams only gives its pages back when it is quiet. History, `Last-Event-ID`, `.retry_ms` and `.keepalive_ms` are as on HTTP/1.1; a client that stops reading is held to the Room's backlog and reset with `CANCEL` at the write limit; a reset, a GOAWAY, a closed connection and a stopping server each end the stream and give its seats back; a handed-over stream counts against `max_concurrent_streams`. **`c.upgrade` is still refused by name on HTTP/2** (the sentence now says "is HTTP/1.1 only"). A server that stops ends each handed-over stream with its last frame and a GOAWAY, written under a cancellation shield (`bulkhead.beginShield` and `endShield` are new in the Bulkhead contract), and a client that gives its window back a byte at a time is a flood and never makes an event be formatted again. Cost: a handed-over stream weighs 6.2 KB at 10,000 opened a thousand at a time (12 KB opened at once, which is not explained yet) and 4.9 KB on top of its connection when it is the only one on it, against 19.6 KB for one parked in its handler; HTTP/1.1's 5,192 bytes and an idle HTTP/2 connection's 9,423 are unchanged to the byte; a build without the flag is byte-identical, a `-Dhttp2` one 5.1 KB larger and 9.8 KB more for a program that calls `eventsFrom`, which pays nothing on HTTP/1.1; 100 subscribers are written 15 to 17 million events a second over HTTP/2 against 18 million over HTTP/1.1 ([`bench/result/http.md`](bench/result/http.md#what-an-event-stream-handed-to-the-http2-connection-costs)).
- **A unary gRPC call is about 30% faster in process, makes one allocation fewer, and a `-Dhttp2` build is 30 KB smaller**: the call reaches the App as what was read and its answer is collected by the framing, where both used to be written as HTTP/1.1 and parsed back ([ADR 253](docs/adr/253-an-answer-is-handed-to-the-framing-that-carried-its-request.md)), and its headers' Huffman is decoded two symbols a lookup, which halved the HPACK share of a call (767 to 773 ns a call, from 1,083 to 1,118). Its metadata is held to the same rules an HTTP/1.1 head is, as it was.
- **In a `-Dtls -Dhttp2` build, a TLS listener offers `h2` and `http/1.1` by ALPN and serves what was chosen** (stage 7 of [the framing page](docs/design/framing.md)): a browser gets HTTP/2 from nilo itself, every route working on it, and a client that sends no ALPN is served HTTP/1.1; one that offers ALPN with neither `h2` nor `http/1.1` in it gets RFC 7301's `no_application_protocol`. A WebSocket stays HTTP/1.1, on a connection of its own. gRPC over TLS is an ordinary TLS listener. An HTTP/1.1 connection over TLS costs what it did (9,370 bytes idle at 10,000 connections against 9,364), an HTTP/2 one 9,564 to 9,581 after a `GET`, so a browser holds about 9.6 KB where six HTTP/1.1 connections held 56 KB; a page of nineteen subresources loads in 77 to 80 ms against 117 to 121 with 20 ms added to every request, and equally on loopback. A build without `-Dhttp2` offers `http/1.1` alone, as it did ([ADR 259](docs/adr/259-http2-is-a-framing-of-every-request.md), [ADR 027](docs/adr/027-tls-is-terminated-in-front.md)). `bench/page_server.zig` and `bench/page_load.mjs` are the page and the Chromium driver, and `bench/mem.py --tls --h2` the idle figure.

### Fixed

- **A connection over TLS no longer waits on a socket that has nothing for a record it already holds.** The record layer takes whatever the socket has and decrypts one record a call, so a client that sent a second frame right behind its first (HTTP/2's `HEADERS` behind its `SETTINGS`, one connection in a thousand) left the server parked for bytes it had read; the wait now answers from the record layer first. A WebSocket over TLS parked in the same wait.

## Released

Every tagged release has a page of its own, written for the person upgrading: what to do before deploying, and what is new. Every entry of a release, the whole account, is that tag's own `CHANGELOG.md`, which the page links to.

- **[v0.7.0](https://github.com/nevindra/nilo/releases/tag/v0.7.0)** ([every entry](https://github.com/nevindra/nilo/blob/v0.7.0/CHANGELOG.md)): a long list of wrong results returned without an error, fixed, and what was missing when a log server was ported onto nilo. A failed statement that committed as success, a delete a search box could empty a table with, pages that repeated rows, a cache hit an old slot could forge, closed; routes per listener, a body limit from configuration, OpenTelemetry tracing and `nilo_proto`, Rooms shared by sockets and event streams, and a Row that reads a feed, a cursor and a column of another table. Seventy-one things to read before deploying, grouped by who meets them there.
- **[v0.6.0](https://github.com/nevindra/nilo/releases/tag/v0.6.0)**: nothing needed in front, and read line by line for what a stranger can do. HTTPS, gRPC, compression and a cross-site check behind an option or a flag; every executor accepting and a response flushed before the connection waits; a Row that carries its parent, its children or a sum; and what a client on the socket could forge, crash or read, closed. Eleven things to read before deploying, listed there.
- **[v0.5.0](https://github.com/nevindra/nilo/releases/tag/v0.5.0)** — the
  roadmap read back against the tree: a Row that says more about its own
  table and `sql.Schema` as the one value that reads it, `nilo.Verified` and
  `jwt.Keyring`, `fetch.Target`, `nilo.Text` and `nilo_check`, `nilo-dev`, a
  queue that wakes its workers. Seventy-nine entries; eight things to read
  before deploying, listed there.
- **[v0.4.0](https://github.com/nevindra/nilo/releases/tag/v0.4.0)** — one
  module, `nilo_job`, and the thirty-odd shapes a second port needed: a
  listing page in one statement, an order chosen from a closed set, a route
  answering once per key, a health page, and the two fixes that let the suite
  run on a Mac. Twelve things to read before deploying, listed there.
- **[v0.3.0](https://github.com/nevindra/nilo/releases/tag/v0.3.0)** — the
  release a real port wrote: migrations as a diff against a snapshot and the
  `db` command, deadlines and an allowance per route, a metrics page, sessions
  that expire, and eleven things to read before deploying, listed there.
- **[v0.2.0](https://github.com/nevindra/nilo/releases/tag/v0.2.0)** — 0.1.0 was
  an HTTP server called zfast. 0.2.0 is a toolkit called nilo, and that server
  is one of its eight modules. Includes what to change when upgrading from
  0.1.0.
- **[v0.1.0](https://github.com/nevindra/nilo/releases/tag/v0.1.0)** — the first
