How to read this

Four rules that make the numbers trustworthy

The thing we're trying to measure is small. An ORM's overhead is often less than 1% of an operation. Meanwhile this machine speeds up and slows down by as much as 8% over a few minutes, just from heat and background work.

So if you run each library one after another and compare, you're not measuring the libraries. You're measuring who happened to go first. Here's what we do instead.

  • 1 · Run every library in the same process, alternating The ORM does a batch of work, then the raw driver does the same batch, then back again — hundreds of times, swapping who goes first each round. We report the middle of all those head-to-head gaps, not the gap between two averages. If the machine slows down, it slows down for both sides at once, and the gap between them stays honest.
  • 2 · Make every library prove it did the work Each one has to add up the same total from the data it read: all the IDs, all the ages, all the email lengths, all the timestamps. Ten libraries in four languages, same number every time. A library that cheats by not actually decoding a field until you touch it can't produce that total. This is what stops "fast" from meaning "did less".
  • 3 · If the gap is smaller than the noise, say so Every gap comes with an error range. If that range includes zero, the answer is "no measurable difference" — not a ranking. Saying "we can't tell these apart" is more useful than inventing an order that won't hold next time.
  • 4 · And the error range alone isn't enough We learned this the hard way, and it nearly went out wrong. The first run gave nilo_sql tidy-looking error ranges that all excluded zero. But when we split that same data into its three passes, the direction flipped: nilo_sql looked 212 ns slower, then 178 ns slower, then 147 ns faster. GORM, Drizzle, Prisma and diesel-async never did that — their gaps pointed the same way every time. So the split doesn't separate a reliable machine from an unreliable one. It separates gaps we can actually measure from gaps that are lost in the noise. From then on, a gap only counts as real if all six measurements — three passes in each of two separate runs — agree on which side is faster.
Two things these rules do not cover

Rule 4 filters noise, not meaning. Six measurements agreeing on a direction tells you the gap is real. It does not tell you the gap is a cost — if two things being compared are limited by different resources, you can get a tight, repeatable, completely meaningless number. Every paired comparison here sends the same SQL over the same connection, so the gaps are costs. But the rule isn't what guarantees that; reading the two code paths is.

And the raw driver isn't always doing identical work — the bias runs against nilo_sql, not for it. On the multi-row tests nilo_sql builds and returns an array of structs, because that's what its API does; the raw driver just adds numbers up as rows arrive and never allocates an array. So nilo is charged for work the reference never did. We're leaving it that way, because db.select returning a slice is the thing being measured — but it means every nilo_sql number here is a ceiling. It also makes finding 1 stronger: building a thousand-element array still lands below what we can measure.

One note about the write tests With Postgres set up normally, a single INSERT takes about 660 µs on this machine, and every library gets the same number. That's because you're not timing the library — you're timing the disk waiting for the write to be flushed. True about the workload, useless for comparing libraries. So we turned that flush off for this throwaway test database, and we report the 660 µs figure here rather than pretending it doesn't exist.

Two of them — SQLx and Prisma — bring their own driver. Their gap to the raw driver is part ORM, part different driver, and we've marked those rows so nobody reads them as an ORM cost.

Part one

Reading data

Six tests, arranged to answer two different questions. The first few keep the table at four columns and increase the number of rows. The last two keep the row count and widen the table to twenty columns.

That split matters. A library whose cost grows with rows and one whose cost grows with individual values look identical on a narrow table, and nothing alike on a wide one — and real applications have wide tables.

Bars are drawn to scale against the slowest library in each test. When a bar is barely visible, that really is how far behind it is.

What the reading tests show

On a single row, almost everything ties. Six of the ten land between 6.2 and 11 µs. The round trip to the database dominates, and any library's own work hides behind it. This is the most realistic test — it's what a normal web request does — and also the least useful for telling libraries apart. The two exceptions aren't noise: Drizzle is 5.4× the fastest and Prisma is 10.7×.

On a thousand rows of twenty columns, the order changes completely. That's twenty thousand values in one answer, so the round trip stops mattering and pure decoding work is all that's left. pg.zig and pgx lead at 0.37 ms. tokio-postgres — which was fastest on a single row — falls behind at 0.48 ms. Prisma takes 8.99 ms, which is 24× the leader.

Some raw drivers cost per value too. Compare node-postgres on the two thousand-row tests: 697 µs for four columns, 2,455 µs for twenty. Same rows, five times the columns, 3.5× the time. That's the driver itself, before any ORM gets involved.

Part two

Writing data

Every write test reads the stored row back using RETURNING. A library that threw that row away would be doing less work than the others, and its checksum wouldn't match.

The insert table is emptied before every single batch, for every library — outside the timer. Two libraries writing the same IDs into a table only one of them cleared is a crash, not a benchmark.

What the writing tests show

Writing separates libraries differently than reading does. When reading, the gaps come from how many values need decoding. When writing one row, there's almost nothing to decode — and yet the spread between fastest and slowest is 4× to 8×. That gap is pure overhead: how many layers a call passes through before it becomes a statement. Nothing amortises it, because there's no bulk work to hide it behind.

Bulk inserts split the field into two strategies. Inserting a hundred rows at once, pg.zig and nilo_sql send one array per column and let Postgres unpack them server-side — the SQL text stays the same length no matter how big the batch is. GORM, Diesel, Drizzle and Prisma build a giant multi-row VALUES statement instead, so the SQL grows with the batch and Postgres has to parse a brand-new statement every time. The cost shows: 135 µs for a hundred rows versus 1,017 µs (Drizzle) and 1,395 µs (Prisma). Per row that's 1.3 µs against 14 µs.

Transactions are where per-statement overhead stops hiding. The tx test does BEGIN, a read, a write, COMMIT — four statements where every other test sends one. Any fixed cost a library charges per statement gets multiplied by four here, which is why Prisma jumps to 9.1× while it was 8× on a single update.

Part three

Deleting data

Deleting empties a table, so we refill it before every batch — outside the timer, and with exactly as many rows as that batch will remove. Seeding a thousand rows to delete fifty would put a differently-sized index under every measurement.

What the delete test shows

This is the simplest operation on the whole page: one integer in, one row back. Nothing to encode, almost nothing to decode. So it's the cleanest look at a library's fixed overhead — how long it takes to turn one function call into one statement and come back.

The spread is 8.1×, from tokio-postgres at 9,165 ns to Prisma at 74,268 ns, for identical database work.

There's a pattern worth noticing across all three languages: query builders are cheapest on the operation with the fewest parameters. diesel-async costs only +5,054 ns here, against +18,443 ns on update and +20,427 ns on insert. Building the parameters, not running the query, is where a query builder spends its time.

For nilo_sql, delete is one of only two places where its cost is actually measurable: +1,673 ns over raw pg.zig, holding steady across all six measurements. It is not an extra round trip — both arms make 4.12 socket calls per delete, measured one arm at a time. So the operation with a single integer parameter is one of nilo's more expensive ones for a reason that is still open, and it is CPU rather than network.

Part four

Memory

Peak memory used by the benchmark process itself — the high-water mark, not the size at the end, so a runtime that has already given pages back doesn't look thriftier than it was. Each process holds one connection and runs the same eleven tests.

This is not "memory per connection", and shouldn't be read that way. It's the baseline cost of the runtime existing at all. For anything deployed as containers, that's the number that decides how many instances fit on a machine.

The main question

Is pg.zig a good Postgres driver?

The answer splits cleanly in two: its decoder is the best in this field, and its protocol handling wastes a network round trip.

The good half shows up on big results. On a thousand rows — narrow or wide — raw pg.zig beats raw pgx and raw tokio-postgres. If your workload is unpacking thousands of values out of a buffer, nothing here touches it.

The bad half shows up on SELECT 1 — a query with nothing at all to decode. There, pg.zig is the slowest of the four raw drivers. When a driver loses on a query that has no content, the problem isn't its decoder. It's on the wire.

The proof, from the bytes on the socket

Here's what each driver actually sends for a prepared statement it has already cached — so there's no parsing to do, and no reason to talk to the server twice: 

pg.zig — two round trips
  sendmsg   5 B   S              →  readv    6 B   Z      ← this trip carries no work at all
  sendmsg  44 B   B E H          →  readv   40 B   2 D C

pgx — one
  write    88 B   B D E S        →  read    40 B   2 T D C Z

tokio-postgres — one
  sendto   32 B   B E S          →  recvfrom 40 B  2 D C Z

That first pg.zig round trip is a lone Sync message, and the driver waits for the server's reply before it sends the actual query. It comes from one line, at conn.zig:243, right on the cache-hit path: 

if (self._prepared_statements.getPtr(n)) |describe| {
    cached = true;
    ...
    // Send a "SYNC" command
    try self.write(&.{ 'S', 0, 0, 0, 4 });
    stmt.buf.reset();
    try stmt.prepareForBind(...);
}

So the irony is: caching the statement saves the server from parsing it, but doesn't save the round trip. One packet out and one back, carrying nothing.

What we learned

Nine things worth keeping

Ordered by how much each one should change a decision. Every number has a run behind it.

1

On nine of eleven operations, nilo_sql's overhead can't be measured at all

From a single row up to twenty thousand values, from bulk inserts to transactions, six measurements across two separate runs couldn't agree on whether nilo_sql or raw pg.zig was faster. On the biggest read test, the first run said nilo_sql was 35 µs faster and the second said 5 µs slower. That's not a result, and saying so is more useful than picking one.

No other library here can say that. GORM, Drizzle, Prisma and diesel-async held their direction across all six — not because they're more consistent, but because their overhead is big enough to see. An overhead that vanishes into the measurement noise is the finding.

2

nilo_sql leads the big reads, but that's the driver's win, not the ORM's

On a thousand rows of twenty columns, nilo_sql is near the top — ahead of raw tokio-postgres, and 5.4× faster than GORM. But raw pg.zig sits right beside it, 1.5% apart. So this is pg.zig's decoder winning, and what nilo's typed layer does is not get in the way. That's still an achievement — just a different one than the ranking suggests.

3

On single-row reads nilo_sql is behind, and it isn't nilo's fault

A single row by primary key is what most web requests do, and there nilo_sql takes 9,917 ns against SQLx's 6,217 ns — 60% behind. But raw pg.zig alone is already 9,405 ns, while raw tokio-postgres is 6,204 ns. The entire gap is in the driver, and it's there before nilo touches anything. Fix pg.zig's round trip and this number moves without changing a line of nilo.

4

pg.zig: best decoder in the field, one wasted round trip

Fastest raw driver at unpacking thousands of values, slowest at SELECT 1. The cause is one line at conn.zig:243 — a lone Sync on the cache-hit path that waits for a reply before sending the real query. It costs about 2.6 µs over a unix socket and 9.2 µs over a Docker bridge. This is the clearest and most fixable gap on the page.

5

Two operations where nilo_sql genuinely pays: insert and delete

These are the only two of eleven where the gap survives all six measurements: insert +2,966 ns and delete +1,673 ns over raw pg.zig. Compare that to update — nearly the same work as insert — where the gap isn't measurable at all.

The obvious explanation was that nilo was sending an extra packet — the gap is almost exactly one unix-socket round trip (~2.6 µs). We tested it, and it's wrong. Counting socket calls one library at a time under strace, both make identical numbers of them: 4.04 per insert, 4.00 per update, 4.12 per delete, matching to two decimal places on every shape. Same packets, same round trips.

So the cost is CPU work inside the process, not time on the wire — and why it lands on insert and delete but not update is still open. All three use prepared statements with the same compile-time plan names and all three return one row. The next probe is a CPU profile, not a packet count. Worth saying plainly: this paragraph replaces a confident-sounding guess with a measurement that killed it, which is why the guess was labelled a guess.

6

GORM is the most expensive ORM here that sits on its own driver

4.1× its own pgx on a thousand-row read, 5.4× on the wide one, and 4–5× on every single-row write: insert 56,194 ns against 12,274, update 52,609 against 10,251, delete 57,867 against 10,649. Worth stressing — pgx itself is not slow. It makes the fewest syscalls per query of any driver here. The entire gap belongs to the layer above it.

7

Prisma is in a different bracket

10.7× tokio-postgres on a single row, 24× on the wide read — 8.99 ms for an answer pg.zig delivers in 0.37 ms. Some of that is fair: it runs its own engine over its own connection, so the gap to node-postgres isn't purely ORM cost. But the practical takeaway holds. If your workload has big or frequent queries, Prisma sets your latency, not Postgres.

8

An ORM can be faster than the driver it's built on

Two cases, both solid across all six measurements. Drizzle is 60,283 ns faster than raw node-postgres on a thousand-row read, and diesel-async is 46,601 ns faster than raw tokio-postgres on the wide one. No magic: the driver's default row object costs more to build than the struct the ORM fills directly. node-postgres builds a name-keyed JavaScript object per row; Drizzle skips it.

Which is why "drop the ORM if you want speed" isn't always true — and why every ORM here is measured against its own driver, not against the fastest driver available.

9

Baseline memory differs by two orders of magnitude

Zig 4,116 kB, Rust 5,916 kB, Go 23,448 kB, Node 341,924 kB — same work, one connection each. Node is 83× Zig. Again, this isn't per connection; it's the cost of the runtime existing. For container deployments that's the number that decides density.

What this page doesn't tell you Everything here is one connection, no pool, no HTTP. That's what makes the per-operation costs clean, and also what leaves the real service question open: throughput, tail latency, and memory per idle connection under load. We already know prepared statements are worth 24% with one request in flight and 67% at a busy pool — because a pooled connection is a serial queue, so time not spent holding it is capacity. Which means any gap on this page could change size, or even direction, once you put a pool and a web server in front of it. That's the next harness.
