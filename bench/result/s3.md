## The control was wrong, and the numbers said so

Worth putting above the results rather than in a footnote, because it is the
part of this run that would have been believed.

`/warm/1k` and `/warm/1m` exist to be subtracted from `/o/1k` and `/o/1m`. In
the first run, **three of the four candidates built the payload once at startup
and handed out the same slice on every request** — Rust via `Bytes::clone`,
which is a refcount bump and no allocation at all. nilo allocated from the
request arena and filled it every time, because that is what its bounded `get`
genuinely does.

So the control was doing less work than the route it is subtracted from, for
three candidates and not the fourth. Every candidate still returned
byte-identical output and passed the payload check, because **the check
compares bytes and the bug was in how they were produced.**

What caught it was not a code review. It was one number that was large in the
wrong place: **Go answered a megabyte 2.2× faster than nilo on `/warm/1m`** —
the route with no object store in it — while losing to nilo on every route that
did real work. A server that is twice as fast at the trivial thing and slower at
everything real is not a finding, it is a measurement error, and the
contradiction with what `bench/result/http.md` already establishes about nilo's
server is what made the file worth opening.

Fixing it moved Go's `/warm/1m` from 16,841 req/s to 7,112, which is the size of
what was being hidden.

Two lessons, and the second is the one that generalises:

- **A control has to perform the allocation the real path performs**, not
  merely produce the same bytes. `/o/1m` sizes a buffer from `content-length`
  and fills it every time; a control that skips that is not "the same work
  minus the object store", it is less work, and the paired difference absorbs
  the whole gap.
- **The sign-agreement rule filters noise, not validity.** `/o/1m − /warm/1m`
  came out at −226,266 ns CPU/req for nilo with all three passes negative and
  tightly clustered (−226,266, −213,300, −250,617). It passed the rule and it
  still meant nothing: the two routes are bounded by different resources — the
  control saturates memory bandwidth, the store route is throttled upstream by
  MinIO — so their difference is not a cost. A rule that catches noise was
  being read as though it certified the number. The test that does certify one
  is in [the subtraction](#what-the-client-costs--the-subtraction).

## The question

Almost nothing you measure about an S3 client is the S3 client. A route that
reads a megabyte out of MinIO and answers with it spends its time in three
places — this language's HTTP server, the round trip, and moving a megabyte —
and the client is the smallest of the three. Compare two languages on that route
alone and the number is mostly a comparison of their HTTP servers.

So the number this file exists for is a **subtraction**, not a row:

> what a client costs = `/o/1k` − `/warm/1k`, at the same size, in CPU ns per
> request

`/warm/1k` and `/warm/1m` answer the same bytes out of the same memory with no
object store anywhere near them. Whatever is left after subtracting them is the
client, and everything else in the table is context for it.

| store | MinIO `RELEASE.2025-09-07T16-13-09Z`, in Docker, published port 9100 |
| load generator | `wrk 4.2.0`, `-t4 -c64 --latency`, 3 × 10s after a 5s warmup |
| candidates | Go 1.26.3 + `aws-sdk-go-v2` · Rust 1.95.0 + `aws-sdk-s3` (axum, `lto=true`) · Bun 1.3.13 + `Bun.S3Client` |

**Everything here is measured through `http://` to a published Docker port.**
Two things follow and neither can be corrected for on paper. A published port
is not a unix socket — the HTTP comparison found the same server 133% faster
over one, and while the *ratios* survived, the absolutes were half. And the
scheme is not cosmetic in this module: plaintext means every payload is really
SHA-256'd, where HTTPS would send `UNSIGNED-PAYLOAD` and carry a TLS record
layer instead. The plaintext numbers therefore include a hash the HTTPS ones
would not, and exclude a cipher the HTTPS ones would.

### Three parties, and the store gets its own cores

The HTTP comparison splits eight cores four and four, server and load
generator. There is a third process here, and one that lands wherever the
scheduler puts it shares silicon with whichever side happens to be busy — so
the split is three, three and two:

```
server 0-2,8-10   |   wrk 3-5,11-13   |   MinIO 6-7,14-15
```

MinIO is moved with `docker update --cpuset-cpus` before the first candidate
starts. `drive.py` says in its first line of output whether it managed it, and
says so loudly if it did not, because an unpinned store makes every candidate
look the same — the one outcome that would tell us nothing.

### The passes are interleaved

Three runs of `/o/1k` followed later by three of `/warm/1k` would put a quarter
of an hour between the two halves of every subtraction, and anything that
drifted in that window would land wholly on one side and be published as what
an S3 client costs. So **one pass is all seven routes back to back**, three
passes, every route warmed before any of them is timed.

A paired difference is reported only if **all three passes agree on its sign**.
A confidence interval pooled over the three would not catch a difference
smaller than the harness can resolve: blocks within a pass are not exchangeable
with blocks in another, because each pass has its own thermal state, and
pooling narrows the interval on an assumption that is false. This rule was not
invented here — it came from the ORM comparison next door, where every one of
one candidate's differences changed sign once the passes were separated, and
every one of them had a pooled interval that excluded zero.

### What every candidate had to do first

Seven routes, verified byte for byte against bytes the harness builds itself,
before any of them is allowed a number:

| route | class | |
|---|---|---|
| `/health` | floor | a constant, no store |
| `/warm/1k`, `/warm/1m` | floor | the same bytes, no store |
| `/o/1k`, `/o/64k`, `/o/1m` | store | one GET each, held whole |
| `/presign` | sign | the signer, no socket |

Then the presigned URL each one returns is fetched by a plain client carrying
no credentials, and has to come back with the object. **A signer that is fast
and wrong fails there rather than winning a row.** All four candidates passed
this, Bun included — it verified clean and then died under load.

One rule is enforced by reading the source rather than by the harness, and it
is a real weakness: each candidate has to *hold* the object rather than proxy
S3's socket into its own response, and a proxy would produce identical bytes
and an identical `Content-Length` while doing strictly less work. All four do
(`io.ReadFull`, `body.collect()`, `arrayBuffer()`, `bucket.get`), but that is a
fact about code I read, not a check the harness makes.
[`bench/compare-s3/README.md`](../compare-s3/README.md) names the fix.

## What the client costs — the subtraction

| pair | nilo (`nilo_s3`) | Go | Rust | |
|---|---|---|---|---|
| `/o/1k` − `/warm/1k` | **+11,814 ns** [+11,960, +11,814, +11,772] | +98,392 ns [+95,748, +98,392, +109,469] | +59,086 ns [+61,026, +59,086, +58,389] | † |
| `/o/1m` − `/warm/1m` | −198,702 ns [−206,630, −198,702, −183,717] | +403,929 ns [+403,929, +401,534, +446,269] | +252,229 ns [+224,110, +291,801, +252,229] | ⚠ |

**This is the number the file exists for.** Reading a 1 KB object out of an
object store and answering with it costs `nilo_s3` **11,814 ns of CPU** beyond
answering the same bytes from memory. The same subtraction is **59,086 ns** for
Rust with the official AWS SDK and **98,392 ns** for Go with its own — so nilo
is **5.0× cheaper than Rust and 8.3× cheaper than Go** on the operation the
module is for.

† **A lower bound, not the cost.** `/warm/1k` saturates the core budget and
`/o/1k` does not, so the subtrahend is measured under hyperthread contention
the store route never sees. That overstates the floor, which understates the
difference — for every candidate, in the same direction, which is why the
*ratios* survive even though the absolutes are conservative.

⚠ **The 1 MB pair is void, and it is worth saying why rather than dropping it.**
It passes the sign-agreement rule with a tight cluster and still means nothing:
nilo's comes out **negative**, and a client cannot cost negative CPU. Both
halves are bounded by the machine and by *different parts* of it — the floor
route thrashes memory bandwidth, where a stalled cycle still counts as CPU time,
while the store route sits waiting on MinIO and stalls less per byte. A route
doing strictly more work then reports less CPU per request than its own control.
No saturation threshold catches this; the check that does is **a client cannot
cost negative CPU, and two candidates running the same operation cannot
disagree about the sign of its cost.** That check is in `table.py`, not in
prose, so the next run applies it whether or not anybody remembers it.

### Signing

`/presign` touches no socket, so it is the signer on its own. Above each
candidate's own `/health`, which subtracts its HTTP server:

| | nilo | Rust | Go |
|---|---|---|---|
| CPU/req above `/health` | **+1,010 ns** | +23,724 ns | +59,676 ns |

**Signing is 23× cheaper than Rust's and 59× cheaper than Go's.** That is
[ADR 0069](../../docs/adr/0069-a-signing-key-changes-once-a-day.md)
paying off — the canonical request is written straight into the SHA-256 rather
than assembled into a buffer first, so there is one hash and one HMAC and no
allocation. Both `/presign` rows are saturated, so read the CPU column and not
the req/s.

## Memory per idle connection

Measured on `/health` with [`bench/mem.py`](../mem.py), out to 10,000
connections, because at 2,000 the marginal and the average still disagree and a
reading that has not converged is a transient rather than a property of the
connection.

| connections | nilo (`nilo_s3`) | Go | Rust |
|---|---|---|---|
| 1,000 | 4,657 B (marginal 4,657) | 21,369 B (marginal 21,369) | 21,623 B (marginal 21,623) |
| 2,000 | 4,663 B (marginal 4,669) | 20,781 B (marginal 20,193) | 21,725 B (marginal 21,828) |
| 5,000 | 4,669 B (marginal 4,674) | 19,911 B (marginal 19,332) | 21,787 B (marginal 21,828) |
| 10,000 | **4,670 B** (marginal 4,670) | **19,825 B** (marginal 19,739) | **21,805 B** (marginal 21,824) |

nilo is **4.2× cheaper than Go and 4.7× cheaper than Rust** per idle
connection, and its marginal and average agree at 10,000 to within a byte, so
the figure has converged. Go's is still falling at 10,000 (marginal 19,739
against an average of 19,825), so its true figure is a little below what is
printed — run it further before quoting it against something close.

**4,670 B is the same number `bench/result/http.md` records for the framework
without `nilo_s3` (4,669),** and the table below reads 4,674 for the same route
on a later run, which is the size of the noise on this axis rather than a
change. Holding a `Store` costs the connection nothing, which is what
[ADR 0070](../../docs/adr/0070-a-fitting-borrows-the-loop.md)'s layer was
supposed to buy.

### What the handler adds, which is the number a deployment sees

The row above is a **floor rather than a total**: by
[ADR 0063](../../docs/adr/0063-a-handlers-stack-is-per-connection.md) a
suspended fiber holds its stack at its high-water mark, so a handler that
actually reads an object adds every byte of stack it touched. Four routes on
the same server, one fresh process each, out to 10,000 connections:

| route | what it does | per connection | over the floor |
|---|---|---|---|
| `/health` | never touches the store | 4,674 B | — |
| `/o/1k` | 1 KB object, into the request arena | 6,731 B | +2,057 |
| `/o/1m` | 1 MB object, into the request arena | 8,782 B | +4,108 |
| `/stream/1m` | 1 MB object, through 64 KB of stack | 12,876 B | +8,202 |

All four converged: marginal and average agree to within 15 bytes at 10,000, and
the pair that matters was run out to there precisely because at 2,000 `/o/1m`
still read 8,837 against a marginal of 8,780.

**The route written to be frugal is the expensive one, and by 47%.**
`/stream/1m` never holds the megabyte and `/o/1m` holds all of it, and the one
that holds it costs 8,782 bytes an idle connection against 12,876. That is
[ADR 0063](../../docs/adr/0063-a-handlers-stack-is-per-connection.md)'s sentence
(in this framework the arena is cheaper than the stack) with a number under it
rather than an argument, and the reason is that the two memories are not held
for the same length of time. The arena is reset at the end of the request and
keeps `arena_keep` bytes; the megabyte is gone before the connection goes idle.
The stack is not reset by anything. Whatever depth the handler reached is
resident for as long as the socket is open, whether the connection is serving or
sitting still.

The pair of routes exists in `bench/s3_server.zig` for exactly this reading, and
the doc comment on `stream1m` says so: *the point of having both routes is that
`bench/mem.py` can price it rather than argue about it.* It has now been priced,
and the answer went against the route that looks careful.

**And it is not the buffer, which is the part worth knowing before anybody tries
to fix it.** `stream1m` declares `[64 << 10]u8` on the stack, which is the
obvious suspect and is 87% of the 8,202 bytes if you count bytes rather than
measure them. Rebuilt with `[8 << 10]u8` and nothing else changed, the same run
gives **12,875 B against 12,876**. 56 KB off the declared buffer moved the
number by one byte. So the cost is the depth of the streaming call path, not
what it carries, and shrinking buffers is the wrong lever. `nilo_fetch` reached
the same conclusion from the other end (−66 bytes for its buffers,
[`fetch.md`](./fetch.md)), which makes this the second time in this repository
that the visible allocation was not the thing being paid for. The experiment was
one line and was reverted; it is recorded here rather than left in the tree.

**A caveat on the arena side, because it is a floor of a different kind.** 8,782
bytes is what an *idle* connection costs, and it is small because the megabyte
was handed back. A connection in the middle of that request is holding a
megabyte, so `/o/1m` is the cheaper route at rest and the more expensive one
under concurrency. Which of the two is right for a deployment depends on how
many of its connections are working at once, and this table answers only the
idle half.

### The harness could not drain a chunked body, so its first answer was noise

Worth recording because the first run of `/stream/1m` looked like a property of
the route: 13,222 B at 500 connections, 16,060 at 2,000, 45,878 at 5,000 and
26,273 at 10,000, which is non-monotonic and no per-connection cost can be.
`bench/mem.py` read `Content-Length` and nothing else, and a streamed route has
no length to announce, so it stopped after the response head and left roughly a
megabyte backed up in every socket. Its own docstring names the failure it was
committing: *a connection with bytes still backed up in it is not idle.* It
drains both framings now, and the corrected run is the row in the table.

**The tell was the shape, not the size.** A number that rises and then falls as
connections are added is not a cost per connection at any of those points, and
that is enough to reject the run without knowing why.

## Bun did not finish, and that is the row

`Bun.S3Client` was the most interesting candidate in the table and the reason
Bun was in it: it is not a JavaScript SDK wrapped round `fetch`, it is native
code in Bun's runtime, written in Zig, doing SigV4 and HTTP the way `nilo_s3`
does. Two Zig implementations of the same thing, with JavaScript only holding
the handler.

It never produced a row. **It reached 27 GB of resident memory and the kernel
killed it, twice**, taking MinIO, a Postgres container and the session driving
the benchmark with it, because the OOM killer was global rather than scoped:

```
16:40:39  Out of memory: Killed process 8234  (bun)  anon-rss: 27,395,204 kB
16:46:27  Out of memory: Killed process 14843 (bun)  anon-rss: 27,268,712 kB
```

That says Bun is the cause. It does not say what in Bun, so the rest was
measured with `bun` confined to a 6 GB cgroup — `systemd-run --user --scope -p
MemoryMax=6G` — so that finding out cost a dead `bun` rather than a dead
machine.

**One route at a time, 5s each, sampling RSS every 200 ms:**

| route | RSS before | RSS peak | req/s |
|---|---|---|---|
| `/health` | 36 MiB | 50 MiB | 297,377 |
| `/warm/1k` | 47 MiB | 56 MiB | 267,644 |
| `/o/1k` | 47 MiB | 159 MiB | 21,997 |
| `/o/64k` | 158 MiB | **4,650 MiB** | 14,587 |
| `/warm/1m` | 4,737 MiB | 4,769 MiB | 4,167 |
| `/o/1m` | 4,798 MiB | **killed** | 256 |

The routes ran in that order in one process, so each row starts where the last
one left it — which is itself the finding. `/warm/1m` did not begin at 4,737
MiB because it needed it.

The growth is not approximately anything. **It is the bytes read, one for
one.** `/o/64k` moved 72,935 objects of 64 KiB — 4,558 MiB — and grew
4,492 MiB. `/o/1k` moved 107 MiB and grew 112 MiB.

**`/warm/1m` is the control that closes it.** That route allocated, filled and
wrote **20,835 megabyte buffers** in the same five seconds and grew **32 MiB**.
So the collector keeps up with allocation fine, at nearly five times the byte
rate of the route that killed the process. What is retained is specific to the
object-store read path.

Two more checks, because "grew" is consistent with three different problems:

- **Not the collector lagging under load.** 3s of `/o/64k` took it from 36 MiB
  to 2,960 MiB. Fifteen seconds idle, plus a request to poke the event loop in
  case collection only runs on activity: **2,936 MiB.** It gave back 24 MiB and
  stopped.
- **Not an allocator keeping pages and reusing them**, which would plateau at
  the working set and could never have reached 27 GB. Four identical rounds:

  | round | after load | after 4s idle | requests | bytes read |
  |---|---|---|---|---|
  | 1 | 2,945 MiB | 2,920 MiB | 45,753 | 2,860 MiB |
  | 2 | 5,677 MiB | 5,652 MiB | 43,445 | 2,715 MiB |
  | 3 | killed at the 6 GB cap | | 7,638 | |

  Round 1 added 2,907 MiB for 2,860 MiB read, a ratio of 1.017; round 2 added
  2,732 MiB for 2,715 MiB, a ratio of 1.006. Nothing comes back between rounds.
  **Bun 1.3.13 retains about one byte for every byte `Bun.S3Client` reads and
  does not release it.**

What was *not* narrowed, because it stopped being worth the machine time: which
half retains — the read, or answering with what it returned.
[`bench/compare-s3/bun/leakprobe.js`](../compare-s3/bun/leakprobe.js) is written
and unrun, and answers exactly that: `/read` reads the object and replies with
its length so the bytes are dropped, `/send` replies with them, `/alloc`
allocates the same 64 KB locally with no S3 at all. **Anybody filing this
upstream should run it first**, because it is the first question a Bun
maintainer will ask.

**What this costs the comparison.** Bun's `/health`, `/warm/*` and `/presign`
are all obtainable, and `/o/1k` alone would survive a full pass — 35 s at 22k
req/s is about 770 MB of leak. `/o/64k` and `/o/1m` cannot be run at all. A
partial Bun column is worth having and is not in this run; it is in the levers
below rather than skipped, because the row it *would* fill is the like-for-like
Zig-against-Zig one this benchmark most wanted.

## nilo's own controls, outside the comparison

`bench/s3_server.zig` carries two routes the other candidates do not, because
they answer nilo's questions rather than the comparison's:

- **`/stream/1m`** — the same megabyte piped from the store to the client
  without ever being held whole. `/o/1m` puts a megabyte in the request arena;
  this puts 64 KB on the stack and moves the object through it. By
  [ADR 0063](../../docs/adr/0063-a-handlers-stack-is-per-connection.md) that
  trade is the wrong way round for an idle connection — arena is per request,
  stack is per connection at the high-water mark — and having both routes is
  what lets `bench/mem.py` price it instead of arguing about it. Chunked, so
  its wire bytes differ from `/o/1m`'s and it is not in the comparison.
- **`/head/1k`** — one round trip with no body coming back, which separates
  what a request to the store costs from what its answer costs.

**Neither was measured in this run.** Both are in the levers below.

### The 32 was a bug in nilo, and it is fixed

Found the cheap way, in the end: re-run one route with the server's stderr
attached instead of sent to `/dev/null`. Every failure was one line.

```
warning: nilo_s3: nilo-test could not be reached: HttpConnectionClosing
warning: handler GET /o/1k failed: Failed
```

**`std.http.Client` pools up to `ConnectionPool.free_size` idle connections,
which is 32, and MinIO reaps them.** The first request onto each corpse gets no
answer at all. std documents `HttpConnectionClosing` as "the client sent 0
bytes of headers before closing the stream. This happens when a keep-alive
connection is finally closed", and nothing retried, so each became a 500 the
caller did nothing to deserve. Exactly 32, deterministic across runs and
processes, because 32 is the pool.

Controlled, because a count that always comes out the same deserves an
experiment rather than a story:

| pool state before the run | non-2xx in 10s |
|---|---|
| warm, straight after a previous run | **0** |
| idle 80 seconds | **32** |

That is precisely the case
[ADR 0067](../../docs/adr/0067-most-of-an-s3-client-is-not-s3.md) decided and
called correctness ("not retrying that once turns every idle timeout into a
spurious error"), and which
[ADR 0070](../../docs/adr/0070-a-fitting-borrows-the-loop.md)'s blanket "no
retries" then swallowed when the policy moved to `nilo_fetch`. Both documents
were right on their own. Nothing re-read the first when ownership moved.

**And the obvious fix was not enough, which is the part worth keeping.** One
retry took 32 down to **13**: when a whole pool goes stale together, the retry
draws a second corpse about as often as a live socket, because an attempt can
only evict the connection it was handed. Bounding the retries by the pool's own
`free_size`, at most one attempt per connection it could be holding, takes
the same run to **0**.

| retry bound | non-2xx after 80s idle | req/s |
|---|---|---|
| none | 32 | 21,262 |
| one | 13 | 21,698 |
| `free_size` | **0** | 21,368 |

Throughput is unchanged across all three: the spread between them is wider than
the difference, and the retry only runs on a socket that was already dead.
`fetch/live.zig` now stands a server that answers once and hangs up, and the
test was watched failing with the retry switched off before it was kept
([ADR 0033](../../docs/adr/0033-a-guard-is-not-a-guard-until-it-has-been-seen-to-fail.md)).

The 52 timeouts on `/warm/1m` are a saturated route against `wrk`'s default 2s
timeout and are not interesting.

## Binary size

The fourth axis, which this file said was not measurable yet. It was: the two
scratch programs it claimed were written did not exist, and writing them took
twenty minutes.

Stripped `ReleaseFast`, two servers with one route each, differing only in
where the bytes come from (`bench/size/s3_none.zig` against
`bench/size/s3_get.zig`, built by `zig build size-s3`):

| | bytes |
|---|---|
| answers from the arena, never names `nilo_s3` | 1,007,496 |
| answers from a bucket | 1,716,072 |
| **what object storage costs** | **708,576** (692 KB, 1.70×) |

**The delta is deliberately the whole of it**, SigV4 and the bucket plus
`nilo_fetch` plus `std.http.Client` plus TLS and the certificate bundle,
because that is the question an operator asks. [`fetch.md`](./fetch.md) is what
splits the layers inside it: 1,688 bytes for the Fitting and 655,600 for
`std.http.Client` and TLS, which leaves roughly **51 KB** that is `nilo_s3`
itself.

And the claim that a program storing nothing pays none of it is checked rather
than asserted: `strings` finds **0** occurrences of `aws4`, `x-amz` or `s3` in
the control and 11 in the other.

## Can the number be pushed further

Ranked, so the next person starts from the ranking rather than from the top.
The first two are worth more than the rest combined, and neither is about the
object store.

1. **The 1 MB write path, and it is nilo's own.** On `/warm/1m` — a route with
   no object store anywhere near it — axum answers **18,160 req/s** and nilo
   **8,215**, at the same core budget and with the control now doing equal work.
   That is 2.2× on nilo's HTTP write path for a large body, it is the single
   biggest gap in the table, and it is not the S3 client's. The hypothesis to
   test first is the arena: `c.arena().alloc(u8, 1 << 20)` per request against
   an arena that resets keeping `arena_keep` bytes means fresh pages and 256
   page faults every time, where Rust's allocator hands back the same warm
   block. Raising `arena_keep` past a megabyte on this route is a one-line
   experiment that either confirms it or kills it. **Not yet run, so the
   explanation is a hypothesis and the 2.2× is the only fact.**

2. **The streamed route's call depth, and the buffer is ruled out.**
   `/stream/1m` costs 8,202 bytes an idle connection over the floor against
   `/o/1m`'s 4,108, so the streaming path is where this module's per-connection
   memory is. Dropping its transfer buffer from 64 KB to 8 KB moved that by one
   byte, so the lever is depth rather than size. That is the same lever ADR 0071
   pulled to halve the framework's own figure, applied to a path nobody has
   looked at yet. Read `files.stream` → `Reading.pipe` → `Ctx.stream` for a frame that
   could wait somewhere shallower.

3. **A partial Bun column.** Five of the seven routes are obtainable and the
   Zig-against-Zig row is the one this table most wanted. It needs the harness
   to accept a per-candidate route set and to record a DNF rather than dying —
   half a day, and it makes the leak reproducible by somebody else rather than
   quoted from here.

5. **`key_max` and `session_token_max`.** Both size stack buffers and both are
   comptime, so this is a lever a *user* has rather than one nilo has. The
   question to answer is how much per connection each is worth, so the defaults
   can be argued about with a number instead of a feeling.

6. **The signer — do not bother.** `/presign` is 1,010 ns of CPU above
   `/health`, against 23,724 for Rust and 59,676 for Go. There is nothing here
   to win, and saying so plainly is the point of ranking it last rather than
   leaving it unmentioned.

Binary size is off this list because it is measured now, above, and folded
into ADR 0018's running total.
